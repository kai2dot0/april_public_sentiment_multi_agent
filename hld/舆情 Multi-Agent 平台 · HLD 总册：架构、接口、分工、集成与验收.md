## 1. 范围与目标

### 1.1 建设目标

建设市场监管舆情监测平台的 Demo，只做框架层：数据采集、多 Agent 编排、并发与可靠性、热插拔扩展、知识层、证据与质量保障。大模型（含嵌入模型）是外部可替换资源，一律经模型网关接入，不训练、不微调。

### 1.2 三条质量承诺（所有模块共同遵守）

1. **可溯源**：每条 Claim 绑定证据（原文片段 / 统计查询 / 规则判定 / 其他 Claim）。报告中的统计数字只能引用指标结果（`fact:metric_result_id` 槽位）；日期、派生数值走各自经校验的槽位（`time`、`derived`）；槽位之外，模型不得自己写数字。
2. **可删除**：来源永久删除内容或账号后立即禁读，所有登记过的副本都要清理，或如实记录为"撤回不到"。账号停用、断流待核验、仓库重置待核验属于临时不可用：只在读取时限制，满足对应的解除条件后恢复，不等同于永久删除。
3. **不丢不重**：崩溃、重启、重复提交、并发竞争下，每个任务只有唯一有效结果。

### 1.3 Demo 边界（大纲 §11）

| 类别  | 内容                                                                                                                                                                                                                                                                                                                       |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

### 2.2 代码仓布局与依赖方向（大纲 §2.4）

```
contracts/   spi/   sdk/   runtime/   capabilities/   adapters/   connectors/   agents/   domain-packs/   apps/
```

- `contracts/`、`spi/` 不依赖任何其他包。
- `sdk/` 只依赖 contracts + spi，不依赖 runtime。
- `agents/` 只依赖 contracts + sdk，不 import connectors。
- `connectors/` 只依赖 contracts + spi + sdk；禁止直接使用 httpx / requests / aiohttp / websockets / socket 等网络库，网络访问一律经 SDK 受控传输句柄。
- `runtime/`、`capabilities/` 不依赖 agents / connectors；`adapters/` 只放基础设施实现。
- **事务内适配器**放在 `capabilities/`（二组），由 `runtime/core/`（一组）的提交段或平台控制变更入口在进程内调用。适配器只依赖 `contracts/` 中定义的"提交上下文"接口（事务句柄、已锁根来源集合、锁层级守卫），不 import `runtime/core/` 的内部模块。
- 依赖方向由 import-linter 在 CI 中强制执行；真正的网络隔离由进程组级网络策略执行（第 2.4 节）。

### 2.3 两条主链

**数据链**（流式段持续运行，产出段按需拉取，大纲 §3.2）：

```
定时表 ─► 采集任务 ─► collector + 连接器 ─► 原始响应(staged) ─► 采集 complete
   ─► 决策表判定 ─► 提交：转正 / PageResult / 规范化任务 / 续采任务 / 覆盖声明 / 检查点
   ─► normalizer ─► 标准文档 + 来源正文 + 传播边 + 互动观测
   ─► cleaner ─► entity-resolver ─► tagger / embedder ─► topic-assigner / clusterer
   ─► topic-framer / topic-tracker ─► risk-detector ─► risk-grader ─► Claim（放行后发 claim.accepted）

report.requested ─► 就绪判定（CaptureCoverage，两级结论）─► ReportInputSnapshot
   ─► report-drafter（内容块 + 槽位）─► 槽位校验 ─► 发布策略（取最严）─► 人工审批 ─► 发布
```

上图是示意顺序，实际按各 Agent 的 Manifest 订阅关系由平台接线。

**控制链**（删除与临时不可用，大纲 §4.12）分两个分支，入口有两个：

```
入口 A：连接器 tombstones[] / 账号控制信号 ─► 采集 complete 第 ⑥ 步：控制状态转换【1】
入口 B：平台派生的控制变更（缺失计数达到删除确认、核验完成解除门控、提交外判定的断流门控）
        ─► 删除确认处理器 / 核验完成检测器 / 断流门控规则【2】
        ─► 平台控制变更入口（独立事务，同一个转换函数）【1】

两个入口进入同一个控制状态转换函数，分两支：

├─ 永久撤回（文档 / 账号删除）
│    控制行 FOR UPDATE ─► 撤回代次 +1 ─► 撤回日志计数行分配序号 ─► 登记扇出责任 ─► 提交
│    ─► 唤醒广播（撤回日志在 PG 是权威，广播只负责唤醒；接收端按序号拉取并补齐空洞）
│    ─► 各存储删除处理器执行（证据、索引、Claim、指标、缓存、报告、导出）
│    ─► 各进程回报连续已处理前沿 ─► 清理完成判定
│    获知即禁读，不等清理完成
│
└─ 临时原因（account_inactive / sync_unverified(epoch) / source_gap(epoch)）
     控制行 FOR NO KEY UPDATE ─► 只递增 availability 版本
     （不递增撤回代次、不分配撤回序号、不登记扇出）─► 读时门控立即生效
     ─► 只能由对应事件解除：账号恢复清除 account_inactive；核验完成且代次匹配才清除
        sync_unverified / source_gap；清除范围级原因不放行未核验文档
```

## 6. 关键流程

### 6.1 采集一个切片（bounded\_slice）

1. 【2】定时表到期 → 调用【1】任务创建 API（I2）。该 API 在作业行锁内复核代次与栅栏，然后建任务。
2. 【2】collector 经 SDK 领取任务 → 连接器经受控传输 `fetch`。每次外部请求前经传输服务 `admit` 准入。实时入口在**实时连接登记成功之后**才开始订阅接收（登记同时返回本作业是否为当前权威作业及指定版本）；受控传输层在帧到达时打接收时间戳、编帧序号。连接器解析出账号控制事件后，立即经受控传输句柄调用 `record_receipt(帧引用, 上游事件身份)`：接收时间戳、入口、连接与追赶标记由 SDK 按帧引用附加，**连接器不能填写时间**；事件在接收记录确认（或放弃重试）后才进入 FetchPage。登记失败或超时不阻塞采集，该事件按"未登记"进入结果包。接收记录一期用于审计与夹具，接收时刻证明只对夹具来源开放（第 1.3 节、分册二 §3）。
3. 【2】原始响应经证据 API（I6）以独立事务 staged 登记：任务行 `FOR UPDATE` → 根来源控制行 KEY SHARE（排序）→ blob 行 → 逻辑对象行；根来源由证据服务推导，锁内复核永久撤回。
4. 【2】collector 组装 FetchPage 结果包，调用 `complete`。
5. 【1】计算段：合法性校验（违规清单）+ 决策表匹配 + 汇总本包全部写入的根来源集合 + 签名材料。
6. 【1】提交段（按步骤顺序；括号内为所调用的二组事务内适配器）：
   - 第 ③ ④ 步：任务行与租约复核，必要时进入受限控制投影；
   - 第 ⑥ 步：对根来源集合的控制行按（范围类型，ID）排序加锁（I7 幂等创建控制行）；控制信号经控制状态转换函数处理，永久撤回分配撤回序号并登记扇出（I7）；接收时刻证明（一期只对夹具来源启用）按上游事件身份经 I7 查询首次接收时刻与追赶标记；来源处于交接核对中时按第 6.8 节处理；需要的计时器（保持回访等）只生成"待登记意图"，**不在本步落库**；
   - 第 ⑧ 步：staged 转正与首次创建种类写正式持有（I5）；目标实例 condemned 时整包返回 `retry_after(blob_condemned)`；
   - 第 ⑨ 步（状态行层级，按第 7.4.1 节的层内顺序）：写 PageResult、覆盖声明、规范化任务；登记存在 / 缺失观测与核验记录（I9），缺失计数达到确认时同事务写待确认撤回记录；登记决策表计时器与第 ⑥ 步生成的计时器意图（I21）。I9 在 M0 末接入，接入前第 ⑨ 步不发起观测登记调用；
   - 第 ⑪ 步：外发箱；
   - 第 ⑫ 步：作业行 CAS 推进检查点，创建续采 / 下一切片任务。
7. 【1】normalizer 处理规范化任务，产出标准文档与来源正文，进入下游流水线。

### 6.2 Agent 任务处理

1. 【1】事件物化 → 生成任务（有序消费者按键占用领取）。
2. 【2】SDK 领取任务 → 【1】Agent `handle()`，经 SDK 调用网关、证据 API、知识服务、状态服务 → 组装结果包。
3. 【1】计算段校验与签名 → 提交段 13 步（派生写入经 I10）→ 外发箱 → 转发器 → Kafka。
4. 冲突与重试处理（SDK 按结局处理表执行，分册二第 2 节）：
   - `control_epoch_changed`：保留租约，按新前提重算，重算次数不超过涉及的控制对象数；
   - `state_version_changed`：重读状态后重算，计入预算；
   - `lease_lost`：放弃任务，由新持有者重做；
   - `retry_after(pg_admission)`：退避后重提；
   - `retry_after(blob_condemned)`：由该种类的写入方重新上传生成新实例后重提，**上传放在计算段之前的"上传准备"阶段**，计算段本身保持只读。来源正文（normalizer 经 SDK 上传）由 SDK 重走上传三步后以同一结果包重提；统计结果、规则决策的顺序为：接收重提 → 写入方（运行时 / 知识服务）在事务外完成上传准备 → 运行时执行只读计算与签名 → 短提交事务，SDK 只做短暂退避后原样重提。上传期间不持任务行或控制对象行锁；实例变化不改变逻辑身份、内容摘要与结果包语义摘要。

### 6.3 报告生成

1. 【1】接收 `report.requested` → 读取 CaptureCoverage、处理前沿与核验状态（I9 查询）→ 就绪判定（完整 / 相对本次观察 / 等待至超时并记录缺口）。
2. 【1】冻结 ReportInputSnapshot（读取经 I17 读时可用性判定）→ report-drafter 生成内容块与槽位 → 槽位校验。
3. 【1】按发布策略决定是否须人工审批 → 发布，生成制品版本。
4. 【1】下载等导出：先经导出登记（I20，二组）登记副本与受控 / 非受控分类，登记成功后才把制品交给用户；制品生成与生成失败的处理归一组。

### 6.4 删除：来源明确的删除事件

1. 【2】连接器识别删除标记，放入 `tombstones[]` → 采集 complete（删除信号的唯一正式路径）。
2. 【1】第 ⑥ 步：控制行 `FOR UPDATE` → 永久撤回、撤回代次 +1 → 撤回日志计数行分配序号 → 登记扇出责任 → 提交 → 唤醒广播。
3. 各存储删除处理器执行：
   - 【2】证据撤回、引用 −1、回收字节；向量 / 全文 / 指纹索引与话题成员删除；话题中心与指标结果失效；网关缓存与反向索引遮蔽；应用侧检索缓存重建；
   - 【1】Claim 标 `source_withdrawn` 并遮蔽 quote；ValidationRecord 标 `affected_by_deletion`；EvaluationRecord 适用性失效；报告制品与 ReportInputSnapshot 遮蔽并重新渲染；ReviewRecord 的复核文本与引语遮蔽；Agent 状态中保存的内容派生数据清除。
4. 【2】各进程按撤回日志序号拉取、补齐空洞、剔除缓存并回报连续已处理前沿 → 判定清理完成。获知删除即禁读，不等清理完成。

### 6.5 删除：缺失计数确认，以及临时不可用的设置与解除

这条路径是大纲 §4.12"删除确认"与"独立删除事务"的实现，不构成第二条删除信号路径：连接器的删除标记仍只经 `tombstones[]`；这里是平台根据缺失观测**派生**出的确认，走同一个控制状态转换函数。

1. 【1】采集提交第 ⑨ 步经 I9 登记缺失观测；I9 按大纲 §4.11 规则计数，返回是否达到删除确认。
2. 【2】达到确认时，I9 在同一提交事务内写"待确认撤回"记录。读时可用性判定（I17）把该记录视为不可读，**获知即禁读**从这一刻生效。
   - **待确认撤回记录一经写入即视为删除确认责任已经确定、不可撤销**（大纲 §4.11"确认后一律按永久撤回处理"）：之后登记的任何 present 都不撤销它，I9 对已有待确认记录的文档不再计数；删除确认处理器只做转换，不重新判定计数。
   - **它不代表永久写屏障已经生效**。永久写屏障以 I16 更新根控制行并提交的时点为生效点（大纲把写屏障建立在根控制行上）。转换前提交的内容写入照常登记完整根来源、受待确认记录的读时禁用，并在永久撤回后由扇出处理器一并清理。
   - 待确认记录记下确认依据（常规缺失确认 / 下界未知按策略计入的"保守来源不可见撤回"）；I16 转为永久撤回时把它一并记入撤回日志与审计，以便与来源明确的删除区分（大纲 §4.12）。
   - 待确认记录未完成转换时，不得宣布永久写屏障到位或全副本清理完成。M1 出口第 3 条"删除后写入被拒"以永久撤回生效为准。待确认记录滞留超过阈值时告警，计入删除探测时延（大纲风险 R24）。
3. 【2】删除确认处理器扫描待确认撤回记录，为每条开启独立事务调用【1】平台控制变更入口（I16），并把"删除该待确认记录"作为本次调用的明确操作交给 I16。I16 的顺序：控制行 `FOR UPDATE` → 撤回日志计数行 → 永久撤回与扇出登记 → 删除待确认记录（状态行层级）；处理器随后提交。I16 按目标状态幂等，处理器崩溃后重跑不会重复分配序号。
   - **目标状态已经达成时**（例如该文档在处理器调用之前已经由墓碑永久撤回），控制状态不变、不分配序号、不重复登记扇出，但调用方交来的明确操作（如删除待确认记录）**仍照常执行**。待确认记录在"该文档已处于永久撤回状态"的事务内删除即可，不要求本次调用就是首次撤回。I16 的两类写入见第 7.4.1 节第 6 款。
4. 【2】临时原因的平台侧设置与解除同样经 I16：
   - 核验完成检测器判定 `sync_unverified(epoch)` 的解除条件满足（文档集合固定为 sync 到达时已存，每篇已核验 / 已永久撤回 / 已登记不可采）后，调用 I16 按代次匹配清除；
   - 断流门控在采集提交之外判定时（例如长时间没有任何提交），经 I16 设置 `source_gap(epoch)` 并把作业置 paused；M1 只设置不解除，M2 起由检测器按来源配置的预授权条件经 I16 解除并恢复作业（生成 partial 覆盖）。
   - **M1 人工恢复采集**（大纲 §4.12 M1 临时规则"清扫上线前不解除、不自动恢复"的解释，项目负责人已拍板）：M1 内来源被门控、作业 paused 时（断流门控或第 6.8 节的接任空档处置），可经项目负责人审批人工恢复**采集**，**来源门控不解除**。运维工具带审批编号调用核验完成检测器的人工恢复接口，后者经 I16 恢复作业：按显式恢复结算（先结算旧周期，再建新周期、重置预算、绑定新的恢复代次），授权依据记审批编号，缺口已持久化披露、覆盖记 partial；`source_gap` 代次与核验切点不变，切点确立前恢复后首次观察到的文档仍按未核验处理，不可读。M2 清扫与核验完成后按预授权条件解除。不带审批编号的请求被拒；没有审批时作业保持 paused（M1 出口第 5 条）。
   - I16 修改作业状态时遵守作业级事务的全部规则（校验 `job_generation` 与代次变更栅栏、跨窗先结算、恢复按显式恢复处理），见分册一 §8。
5. 采集提交内识别到的临时原因（账号停用 / 恢复、sync 帧、游标过期导致的断流、同域接任空档）仍在第 ⑥ 步直接处理；同一提交内写入的来源级记录（核验代次等）按第 7.4.1 节第 3 款的来源级断言。

### 6.6 作业代次变更（例如连接器升级）

【1】执行协议全流程（大纲 §4.11）：

1. 登记栅栏与默认终结目标；
2. 锁旧任务并绑定终结目标；
3. 改代次，旧代次心跳不再续租；
4. 扫尾。

【2】配合两件事：计时器只经任务创建 API 新建任务；连接器新版本经影子期验证。

### 6.7 保守保持的回访

1. 【1】第 ⑥ 步**新登记**保守保持时，控制状态转换函数输出"待登记的回访计时器"（立即到期，带 hold\_id）；提交段在**第 ⑨ 步**经 I21 写入，与控制效果同一事务提交。**第 ⑥ 步内不写计时器、不建任务。**
   - **并入已有保持**时不另建在途回访，也不重置已有的退避或核验预算。
2. 【2】定时服务在独立事务中经任务创建 API（I2）创建回访任务。
3. 【2】collector 执行账号状态回访；结果经【1】提交路径写回保持记录。

### 6.8 位置域交接（M1，大纲 §4.7 第 ⑥ 步"单一权威位置域 + handoff\_epoch"）

适用于比较基准为"单一权威位置域"的来源（例如 Jetstream 切换实例）。大纲要求：建立 handoff\_epoch 时记录旧域最后已处理位置与新域起始位置；无法证明两者之间无遗漏时，对跟踪集合中的账号登记交接核对保持（不新增禁读，只阻止清除），核对期间清除类信号一律并入保持、不生效。账号可能有几千个，一次性在一个提交事务里全部登记会让事务和锁持有时间失控，所以按下面的等价方式实现：

1. 【2】连接器按大纲 §4.11 在覆盖信息与位点中报告本包所在的位置域；**实时连接切换实例时，显式报告"本作业的实时连接从位置域 X 切换到 Y"**，附 X 的最后已处理位置、Y 的起始位置与位点映射验证结果。位置模式下由来源配置指定该来源的**权威作业**（来源级指定，每次改指定生成新的指定版本号，分册二 §3）：只有它的显式切换报告能移动权威位置域；改指定到另一作业后，新作业带**接任报告**（所在位置域 Y 与本作业在 Y 域的**连续接收起点**：本作业在该位置域内，自最近一次连续性中断以来向上游请求续接、并被上游接受的起始游标——不是第一条收到的事件的位点。游标失效后的 resync 或检查点迁移、事前审批的强制跳过、作业代次变更中不能逐位对应的检查点迁移、实时连接切换位置域，都算连续性中断，起点改为中断后实际续接的游标；上游对续接游标给出过期类提示的按游标失效处理，不作为起点；起点由第 ⑫ 步随检查点保存，新作业没有检查点时取本会话请求并被接受的起始游标；比较时按 Manifest 写明的续接语义（是否包含与游标相等的事件）对齐，过滤订阅造成的位点跳跃不算空档）。**两种报告都按检查点判断、重复携带，直到被正常提交**：连接器在每个包里比较检查点记下的位置域与本包所在位置域，不同时带显式切换报告（X 的最后已处理位置取自检查点）；比较实时连接登记返回的权威作业指定版本与检查点记下的版本，本作业新成为权威作业、检查点里还没有这个版本时带接任报告。带报告的包以正常结局提交时，第 ⑫ 步无论位点是否推进，都在检查点记下本包的位置域、指定版本与连续接收起点；违规结局与未提交的包不记，报告随后续包再次带上；第 ⑥ 步对重复的报告幂等。同一个包同时带两种报告时，先按接任处理，显式切换报告只作审计。
2. 【1】**只有权威作业的显式切换报告或接任报告才建立 handoff**：
   - 第 ⑥ 步在来源控制行锁内核对本包作业是第 ⑥ 步执行时的权威作业（经 I7 即时授权查询，口径见本步末条），且当前权威位置域等于 X 时，登记 handoff\_epoch（两端位置、handoff 建立时刻），把权威域改为 Y，并经 I7 以一条集合式插入保存本次交接的**账号快照**（即大纲所说跟踪集合中的账号：该来源下快照时刻有正式或 staged 文档的作者账号，加上本包条目的作者账号，且尚未永久撤回）；需要交接核对时只登记"交接核对进行中"，**不逐账号建保持**；
   - 锁内发现权威域已经是 Y（同一切换已登记）时按幂等处理；既不是 X 也不是 Y 时，本包按非权威域处理；
   - **非权威作业的显式切换报告不建立 handoff**：本包按非权威域处理并告警；
   - **接任报告**：锁内核对本包作业是当前的权威作业后：
     - 来源控制行记下的权威域建立依据已是本作业、本指定版本时（重复的接任），只做记录；
     - 当前权威域为空（来源首次启用）：只设权威域为 Y 并记下建立依据，不建立 handoff；
     - 当前权威域不等于 Y（跨域接任）：以锁内的当前权威域为旧域 X，旧域最后已处理位置记为"未知"，按"无法证明无遗漏"登记 handoff\_epoch、改权威域为 Y 并记下建立依据、保存账号快照、登记"交接核对进行中"，其余同显式切换；
     - 当前权威域已等于 Y（同域接任）：比较接任报告中的连续接收起点与**建立依据作业**（来源控制行记下的、最近一次在第 ⑥ 步建立或确认权威域的作业；该行已在锁内）检查点中 Y 域的最后已处理位置（同域位点可比，检查点不加锁读取）。起点不晚于后者时只做记录并更新建立依据；晚于后者，或该作业检查点不在 Y 域、取不到时（空档左端记为"未知"），**在本次提交事务内处理接任空档**：
       - 第 ⑥ 步经控制状态转换函数对该来源设置 `source_gap(新代次)`，登记一条接任空档记录（该代次、两端位置、建立依据、登记时刻），并更新建立依据（来源控制行已按接任报告取 `FOR NO KEY UPDATE`，不升级）；
       - 第 ⑨ 步经 I9 登记该核验代次，**切点记为"未确立"**：连续接收起点只用于判断接任是否连续与空档审计，不作为该代次的 `verification_cut_at` / `cut_position`。切点必须是本次恢复中可靠增量路径重新衔接、能保证其后变化被持续覆盖的边界（大纲 §4.11），由二组的恢复流程在可靠增量路径重新衔接时确立；未确立之前，缺口开始后经任何路径首次观察到的文档一律按未核验处理；已确立的切点之后增量衔接再次失败，保持门控或建立新核验代次，不沿用中断路径的切点；清扫集合按最终有效切点确立时的快照计算；
       - 第 ⑫ 步执行**接任空档处置**（表外作业处置，清单见分册一 §6）：它是大纲 §4.12 M1 断流临时规则在提交内的执行点，不是决策表的一行，决策表本身不变。本包的合法性结论与决策表匹配行照常记入 PageResult，`cycle_has_success` 按本包事实设置，另记处置原因"接任空档"与本次 `source_gap` 代次；检查点按决策表结论推进，并记下位置域、指定版本与连续接收起点；作业按作业级事务规则先跨窗结算、再转 paused，不创建续采或下一切片任务；第 ⑨ 步不登记本包决策表产生的计时器（冷却恢复等），第 ⑥ 步生成的保持回访计时器照常登记；
       - 本包若从第 ③ ④ ⑫ 步转入受限投影，不执行接任报告与显式切换报告的任何效果（权威域、建立依据、空档记录、门控、作业处置），报告随后续包重复携带；
       - 不在该提交中另开 I16 事务，提交回滚时这些效果一并回滚。M1 只设置不解除（可按第 6.5 节经审批人工恢复采集，门控不解除）；M2 起由二组按恢复流程确立切点、清扫，并由核验完成检测器按预授权条件经 I16 解除并恢复作业（大纲 §4.11、§8.3）。接任空档门控由一组在提交内设置，二组不负责设置，只负责其后的核验与解除；
   - 位置域不等于当前权威域、又没有显式切换报告或接任报告的包，**不建立 handoff**：其中的账号临时原因事件按大纲只做记录，设置类登记保守保持（大纲"非权威、也非旧域的位置域事件一律不改变状态"）；墓碑与账号永久撤回照常按目标状态处理；
   - 切换包内按位点顺序处理：旧域部分在登记 handoff 之前按旧规则处理，新域部分在之后处理；
   - 旧域在 handoff\_epoch 之后迟到的账号临时原因事件无操作（墓碑与永久撤回照常处理）；
   - **即时授权查询的口径**：I7 的即时授权查询只能在取得来源控制行锁之后执行，判定时刻由该条服务端查询语句确定（按语句执行时已提交的最新指定版本），不接受连接登记时刻、请求开始时刻或调用方指定的历史时刻，并返回命中的指定版本（记入回执与审计）。该语句就是本次切换 / 接任的授权判定点：改指定在它之前提交，旧作业的报告不建立 handoff；在它之后提交，本次已授权的事务照常完成，新作业的接任在同一来源控制行锁之后执行。改指定与第 ⑥ 步由来源控制行锁与语句快照串行，不需要指定版本的生效时刻（v0.11 为首次资格加的生效时刻、版本前沿与按接收时刻的历史查询，v0.12 已移入接收时刻证明的启用前置条件，分册二 §3）。
3. 【1】**承接本次交接的核对责任（同一个幂等操作，第 ⑥ 步与后台分批承接共用）**：承接只适用于按位置域比较新旧的账号临时原因 `account_inactive`；`sync_unverified` 与 `source_gap` 按代次设置和解除，不建交接核对保持。此后第 ⑥ 步处理该来源账号的 `account_inactive` 信号（含回访结果写回）之前，若该账号在本次快照中、尚未永久撤回、且该原因还没有记下本次 handoff\_epoch：
   - 该原因已有未关闭保持（保守保持或上一次交接的核对保持）时，**复用原 hold\_id**，在保持上记下本次 handoff\_epoch：保守保持不降为交接核对保持，不另建在途回访、不重置预算；此后清除类一律并入，回访有效性还须晚于本次 handoff 建立时刻（大纲 §4.7 第 ⑥ 步）；
   - 没有保持时，新建交接核对保持，**以 handoff 建立时刻作为登记时刻**；回访计时器由转换函数输出、第 ⑨ 步落库；
   - 该原因已有本次 handoff 的完成记录时不重新打开；账号已永久撤回时只记录"核对责任被永久撤回覆盖"，不建保持、不登记计时器；
   - 经 I7 在该账号控制行锁内把快照中该账号记为"已承接"（锁层级见第 7.4.1 节）；
   - 然后按大纲规则处理该信号：清除类并入、不生效；设置类照常应用并按规则并入。效果等同于"登记 handoff 时已为全部账号建好保持"。
4. 【1】**来源控制行的锁模式在计算段确定**（不先读后锁）：本包含显式切换报告或接任报告，或要设置 / 清除 `source_gap` 时，第 ⑥ 步对来源控制行取 `FOR NO KEY UPDATE`；否则，只要处理单一权威位置域来源的账号临时原因信号（含回访写回），就取 `FOR SHARE`；都不涉及时不加锁。位置都在文档 / 账号控制行之后、撤回日志计数行之前。两种模式互斥，保证第 2、3 步串行；普通内容写入不对来源控制行加锁。来源控制行被大量提交取 `FOR SHARE` 会产生 multixact，纳入现有监控。
5. 【2】核验完成检测器按**账号快照**分批（每批一个独立事务）经 I16 执行第 3 步的同一幂等操作：I16 对来源控制行取 `FOR SHARE`，锁内跳过已记下本次 epoch 或已永久撤回的账号；回访计时器只为本次实际新建的保持登记（由转换函数输出决定）。快照内每个账号都已承接（或已永久撤回）后，经 I16 以 `FOR NO KEY UPDATE` 在锁内复核快照，然后结束"交接核对进行中"；各保持此后按各自的回访关闭，个别转人工的不阻塞结束。快照之外、交接后新出现的账号不承接。
6. 【1】交接核对进行中又收到权威作业的显式切换报告或跨域接任报告时，按第 2 步登记新的 handoff\_epoch 与新快照；未关闭的保持记下新 epoch（复用原 hold\_id），不重复建保持。
7. 【2】排序域变化对应的核验代次（建新代次，或验证无缝切换）按大纲 §4.11 同步处理。

#### 7.4.1 事务内接口与锁约定

这是两组在同一个数据库事务里协作的规则，锁序错误会导致死锁或删除后写入，所有跨组调用都要满足。全局锁序以大纲 §4.7 为准：**任务行 → 键占用行 → 控制对象行 → 撤回日志计数行 → blob 行 → 逻辑对象行 → 状态行 → 序号计数器 → 作业 / 检查点行**。

1. **运行位置**：事务内适配器以库的形式运行在调用方进程内（编排器的提交段，或调用 I16 的二组平台服务），接收调用方的事务句柄（提交上下文）。适配器**不开新连接、不提交或回滚、不做网络调用**；每次调用声明所属锁层级，受锁序守卫约束。CI 用静态检查加运行时守卫验证这几点。
2. **第 ⑥ 步锁集合**：本包**全部写入**的根来源都要纳入：Claim 引用的证据、状态写入、`derived_writes[]`、staged 转正、提交事务内首次创建的对象。锁集合 = 这些写入的根来源文档控制行 ∪ 作者账号控制行。计算段汇总该集合并写入签名材料；第 ⑥ 步按（范围类型，ID）排序一次性加锁：普通引用取 KEY SHARE，控制变更目标按大纲取所需的最强模式（永久撤回 `FOR UPDATE`，临时原因 `FOR NO KEY UPDATE`，两者都涉及取 `FOR UPDATE`），不升级。**来源范围控制行不入锁序**（大纲 §4.12）：普通写入路径不对它加锁；它只由控制状态转换更新，更新时排在文档 / 账号控制行之后、撤回日志计数行之前；交接账号快照紧随来源控制行之后（第 ⑥ 步与 I16 相同）。它的锁模式在计算段确定（第 6.8 节第 4 步）：含显式切换报告、接任报告，或设置 / 清除 `source_gap` 时，一开始就取 `FOR NO KEY UPDATE`；否则处理单一权威位置域来源的账号临时原因信号时取 `FOR SHARE`；两者互斥；不得在即时授权查询或锁内状态读取之后升级锁模式。
3. **提交内适配器不自己锁控制行**：I5、I9、I10、I21 写入前断言"本次写入的根来源 ⊆ 第 ⑥ 步已锁集合"，不满足即判为程序错误、整事务回滚并告警。**来源级记录**（`source_gap` 代次的核验记录、接任空档记录、来源级覆盖记录）的根来源是该来源控制对象，断言改为"本事务已在第 ⑥ 步以 `FOR NO KEY UPDATE` 锁住该来源控制行"；未锁同样按程序错误回滚并告警。锁序守卫登记来源控制行的锁模式。
4. **各适配器的锁层级**见下表。

| 适配器              | 层级                               | 说明                                                                                                                                                                                                                                                             |
| ---------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I7 控制对象表与扇出      | 控制对象行 →（来源控制行之后）交接账号快照 → 撤回日志计数行 | 控制行先 `INSERT … ON CONFLICT DO NOTHING` 幂等创建再加锁；扇出登记随永久撤回在计数行之后写入。交接账号快照的生成与"已承接"标记也由 I7 提供：快照在切换包的第 ⑥ 步以一条集合式插入生成（账号集合见第 6.8 节第 2 步）；"已承接"标记在锁住该账号控制行之后写入；快照的锁层级在来源控制行之后、撤回日志计数行之前，第 ⑥ 步与 I16 相同。权威作业指定的即时授权查询只读传输服务保存的指定表，不加锁、不占锁层级，在来源控制行锁之后执行（第 6.8 节第 2 步） |
| I5 证据库           | blob 行 → 逻辑对象行                   | 引用取 blob KEY SHARE；转正取逻辑对象 `FOR UPDATE`                                                                                                                                                                                                                        |
| I9 核验与观测、待确认撤回记录 | 状态行层级                            | 按（表，业务键）排序                                                                                                                                                                                                                                                     |
| I10 派生写入         | 状态行层级                            | 按（表，业务键）排序                                                                                                                                                                                                                                                     |
| I21 定时登记         | 状态行层级                            | 按（表，业务键）排序；不持作业锁再取更靠前的行；提交段只在第 ⑨ 步调用（第 ⑥ 步只生成计时器意图），I16 只按转换函数输出调用                                                                                                                                                                                             |

**状态行层级内部的固定顺序**：一组状态行（Agent 状态、PageResult、覆盖声明）→ I9（核验与观测、待确认撤回记录）→ I21（定时）→ I10（派生写入，第 ⑩ 步）；同一张表内按业务键排序。锁序守卫按此顺序注册。

1. **提交路径外的写入**（I6 staged 登记与实例改绑、平台服务内的持久缓存填充如网关精确缓存与知识服务缓存、门面的独立写入）：根来源由服务端按证据身份与父证据推导，调用方传入的集合只用于核对，不一致即拒绝；锁序为任务行 `FOR UPDATE`（有任务时）→ 根来源控制行 KEY SHARE（排序）→ blob 行 → 逻辑对象行；**在锁内复核永久撤回**，已撤回即拒绝写入；屏障覆盖到最终写入，不只覆盖取数阶段。worker 进程内的缓存不取数据库锁，按分册二 §5 的缓存临界区与前沿复核处理。
2. **平台控制变更入口（I16）**：在调用方开启的独立事务中执行，顺序为控制对象行 →（来源控制行 → 交接账号快照）→ 撤回日志计数行 → 所需状态行（按上面的层内固定顺序）→ 作业 / 检查点行（如需，放在最后）。I16 返回后调用方不再追加任何写入，直接提交。I16 的写入分两类：
   - **随控制结果产生的写入**（扇出登记、新建保持的回访计时器、覆盖记录、交接快照的"已承接"标记）由转换函数的输出决定，只在本次实际改变状态时执行；
   - **调用方的明确操作**只限于与控制结果无关的清理（如删除待确认撤回记录），控制状态按目标状态幂等，目标已达成时照常执行；回访计时器不属于明确操作，I16 不因调用方传入登记请求而登记计时器；
   - 请求本身无效时（例如按代次清除时代次不匹配），整次调用不写入并返回拒绝，由调用方回滚；作业代次或栅栏不匹配时仍按"只登记控制状态、不改作业"处理。
3. **锁序断言**：每条跨组调用路径都要有锁序断言用例，纳入共享 CI 门禁（第 8.4 节）。

#### 7.4.2 连接器 `normalize()` 的执行形态（I15）

- normalizer worker 按连接器制品摘要分组；**每个进程只经 SDK 插件加载器加载一个连接器制品**，规范化任务按连接器路由到对应的组。
- **路由规则**：规范化任务携带产生该原始响应的连接器制品摘要（与该采集任务执行配置锁中钉定的版本一致），按它路由；连接器升级时，旧组在其规范化任务全部完成之前不退役。
- `normalize()` 只返回 NormalizationBatch：不写来源正文、不推进检查点、不访问网络。标准文档与来源正文在 normalizer 自己的 complete 中提交。
- 理由：normalizer 不需要 import 连接器包（满足 `agents/` 不 import `connectors/`），也不需要为规范化单独开远程调用；按制品分组后，连接器升级时新旧版本的规范化互不干扰。

### 7.5 为什么这样分

1. **沿契约切开，两组在接口处会合**。一组定义并执行"提交到底收什么、怎么判"（契约、计算段、提交段、决策表），二组按冻结接口实现"东西怎么进来、存在哪、怎么删"（SDK、传输、连接器、证据库、扇出）。切分线与代码依赖方向（§2.2）一致：`contracts/` 在一组，`spi/` 与 `sdk/` 在二组，跨组改动只发生在少数接口上。
2. **正确性核心必须由一个组整体负责**。提交段 13 步、全局锁序、代次变更协议、控制状态转换、决策表执行之间高度耦合，一处改动牵动其他几处。拆给两个组会在锁序和事务边界上反复返工。所以这些全部归一组；二组以事务内适配器的形式提供证据库、控制对象表、核验记录、派生写入、定时登记操作，并遵守第 7.4.1 节的锁约定。
3. **"生产 Claim"和"校验 Claim"放在同一个组**。Agent 产出 Claim，运行时校验 Claim（引用检查、证据种类、血缘闭包），报告消费 Claim。三者在一组内闭环，Agent 的写法和校验规则不会互相打架。一组的工作重心随时间转移：M0 主攻运行时，M1 主攻 Agent 与报告，人员技能可以按阶段配置。
4. **"数据进出"放在同一个组**。连接器、受控传输、证据库、网关、知识服务、删除扇出都在处理"外部数据进入平台、在平台内留下副本、最后被删干净"这一件事。放在一个组里，删除扇出的完整性（每个存储都有处理器、每份副本都可追踪）由同一批人负责到底。
5. **每个里程碑负荷都均衡**。按大纲估算，两组在每个里程碑的负荷都不超容量（M0 3.8 / 4.2，M1 5.2 / 5.4，M2 2.0 / 2.0，M3 0.8 / 0.9）。二组在 M0 不必等一组全部定稿：契约分两批冻结（第 1 周、第 2 周），二组先按第 1 周冻结的接口开发。
6. **删除义务按"提交路径内 / 外"切**。删除是唯一横跨两组的专题。控制状态的每一次改变都经一组的同一个转换函数（提交内第 ⑥ 步，或提交外的平台控制变更入口）；提交事务外的扇出、缓存、门控、核验、清扫归二组。每个存储的删除处理器由该存储的主责组实现，避免"别人替我删我的表"。

### 7.6 各组的着重点（细节见各分册）

**一组：内核与智能组**

- **提交路径的正确性是第一优先级**。M0 硬判据大部分落在一组，全部都是"不得带条件通过"的硬项（第 9.2 节）。
- 严守全局加锁顺序和"不升级锁模式"。每个新事务路径都补锁序断言测试；第 ⑥ 步锁集合覆盖本包全部写入的根来源。
- **幂等是默认要求**：回执按摘要幂等，控制信号按目标状态幂等，受限投影按（任务，租约代次，语义摘要）幂等，平台控制变更入口按目标状态幂等。
- **决策表与违规清单的完备性**：以显式笛卡尔积穷举全组合（bounded\_slice 维度），是 CI 门禁。新枚举值合并时，强制同步补表或补清单。
- **控制状态转换规则最密集**（比较基准、保守保持、回访覆盖证明、接收时刻证明）。建议 M0 第 1 周先写夹具，再写实现。
- **Agent 侧的着重点**：
  - 规则定级，模型只解释；
  - 统计数字只来自指标结果，日期与派生数值走各自的校验槽位；
  - quote 定位与歧义标记；
  - 强制依赖标志不得清除；
  - 每个必做谓词都要有带样本量 n 与区间的逐条评测记录。

**二组：数据与能力组**

- **SDK 和受控传输要忠实实现协议**：重试与回执幂等、各结局的处理、心跳停止指示、首次接收时刻与追赶标记。
- **连接器只报事实，不做决策**：状态映射要逐一过夹具；线解码保留未知枚举值交给违规清单；Jetstream 游标语义、AppView 缓存新鲜性、RSS 条件请求都是易错点。
- **限流的权威在 PG**：令牌余额、补充基准与冷却都以 PG 为准，连接器在访问网络之前经传输服务准入（短事务原子扣减）；Redis 只作带有效期的拒绝镜像，过期、缺失或无法确定有效期时回到 PG 判定；Redis 丢失既不能凭空多出额度，也不能让采集永久停摆。
- **接收记录要忠实、不阻塞采集**：账号控制事件在收到时立即登记接收记录，时间戳由 SDK 附加，首次接收时刻取全部记录中最早的一条，追赶标记如实置位与清除；登记失败不阻塞采集。接收时刻证明一期对真实来源禁用、只对夹具来源开放，能力闸门由一组在计划解析中执行（第 1.3 节、分册二 §3）。
- **注册先于领取、重启要收尾**：worker 注册成功前不领取任务；容器重启后由新监督器为前任进程核对并退役（分册二 §5）。
- **worker 侧的撤回接收状态经平台服务登记**：进程注册、前沿回报、监督器退役确认都经撤回接收登记服务；缓存临界区内只用本地已拉取的撤回日志复核，不发网络请求。
- **资源隔离要真隔离**：网络策略默认拒绝、按角色放行；cgroup 超限终止；缓存目录可验证清空。"进程活着但心跳断开""退出后缓存目录仍在""旧进程恢复"三种情形，都不得宣布清理完成。
- **证据库的引用记账要严格**：每个持有关系恰好一次 +1、至多一次 −1；回收与新引用并发时不误删；上传与等待不得在持任务行锁的事务内进行。
- **事务内适配器严守锁约定**：只用调用方事务、只在声明层级取锁、写入前断言根来源已锁（第 7.4.1 节）。
- **删除扇出要无遗漏**：凡保存内容派生数据的存储（包括网关缓存、应用侧检索缓存）都要登记删除处理器，门面写入 API 都要执行屏障（CI 检查两者对应）；导出区分受控与非受控副本。
- **读时门控与逐文档核验**：门控范围覆盖派生对象、检索结果与待确认撤回记录；新帖凭 `new_after_cut` 证明可读，不能因断流后门控而永久不可读。

## 8. 集成方案

### 8.1 原则

1. **契约先行**：契约分两批冻结（M0 第 1 周、第 2 周），冻结前两组只做 adapter 与夹具准备。
2. **Fake 先行，事务内适配器例外**：按桩化规范（Null / Fake / Real 同工厂），网络接口与库接口的提供方在冻结后一周内交付可运行的 Fake，使用方先对 Fake 开发，Real 就绪后切换工厂配置，业务代码不改。**事务内适配器（I5、I7、I9、I10、I21）不做 Fake**，按第 7.4 节时点直接交付最小真实实现。
3. **主干集成**：单仓库、主干开发；功能未完成时用工厂切换或部署范围清单控制，不用长分支。
4. **门禁共享**：两组共用同一套 CI 门禁（§8.4）。任何一组破坏门禁，主干即视为不可用。

## 9. 分里程碑验收清单

### 9.1 验收方法

- **证据**：每项验收都要有可复现的证据，包括 CI 任务与测试名、夹具运行记录或演示记录。证据登记在第 10 章的进度表。
- **单一主责**：每个条目只有一个主责组和一名负责人，对条目整体通过负责；配合方只对列明的子项负责。由多块组成的条目拆成编号子项（附录 C），每个子项也只有一个主责。
- **硬判据**：M0 硬判据不得带条件通过（大纲 §13）。软判据允许带登记缺陷进入 M1，但必须在规定时点前销项。
- **验收人**：项目负责人验收；有配合方的条目，由配合方接口负责人对其子项交叉确认。
- **出口评审**：里程碑出口评审时，本章该里程碑的全部条目都须为"已验收"，或按规则登记为允许遗留。

## 11. 变更流程

### 11.1 四级变更

| 级别                        | 情形                                                 | 审批              | 要求                                     |
| ------------------------- | -------------------------------------------------- | --------------- | -------------------------------------- |
| 一级：组内实现细节                 | 在分册"推荐实现"范围内的调整；在分册列出的验证候选之间做选择（如各分册 0.5 节技术验证的候选） | 组内代码评审          | PR 写明改动与测试；选型结论登记到第 11.4 节的疑问登记表       |
| 二级：替换推荐实现，或引入新的第三方组件 / 服务 | 改变分册推荐方案（**即使不改跨组接口**）；在验证候选之外选型；引入任何新的第三方库或服务     | 本组组长 + 项目负责人    | 提交"实现变更说明"：动机、方案对比、影响面、测试与回退方案；通过后更新分册 |
| 三级：跨组接口 / 契约变更            | 修改 `contracts/`、`spi/`、本总册接口清单或第 7.4.1 节锁约定        | 双方接口负责人 + 项目负责人 | 登记兼容性与返工量；同步更新总册、两本分册与契约测试             |
| 四级：触及大纲冻结范围               | 第 2 章承诺的语义与边界、4.7 提交协议、控制对象两种处置、作业代次变更协议、删除确认规则    | 按大纲附 A 重新进行四方评审 | 评审通过前不得合入                              |

补充规则：

- 引入大纲 §10 技术选型之外的组件（数据库、消息、检索、编排框架、Agent 框架等），至少按二级处理；影响八条底线或已承诺语义的，按四级处理。
- 开发中发现大纲规则在所选技术上无法直接落地，例如来源协议的实际帧类型与大纲描述不一致，先按三级登记差异，再判断是否升到四级。

### 11.2 联调问题处理

- **牵头**：每个接口由提供方的接口负责人牵头定位。
- **定位方法**：契约测试通过**不等于**问题在使用方。先做最小复现，查看调用记录与事务边界（哪个事务、哪把锁、哪次提交），确定根因后再判定归属；属于使用方误用的转交使用方。
- **补测试**：问题关闭前，提供方把该场景补进契约测试，防止复发。

### 11.3 超期处理

按第 10.2 节与大纲 §13 的滚动预测规则执行。释放调节阀必须伴随任务转交。例如二组在 M0 超期时，由一组用 M0 余量接手校验库骨架或扇出登记。

### 11.4 技术疑问与异议反馈

目的：开发人员对推荐技术、不采用的技术或其理由有疑问时，尽早提出、尽早解决，不要带着疑问开发，也不要私下换方案。

- **何时提**：任何时候都可以提。M0 第 1 周安排一次 HLD 走读会，两组分别逐章过本组分册，集中收集疑问；技术验证（各分册 0.5 节）的结论也在这里登记。
- **在哪提**：Confluence 上的"技术疑问登记表"，按下表字段填写：

| 编号  | 提出人 | 日期  | 涉及文档与章节 | 疑问或异议 | 提出人的建议方案（可选） | 影响范围（本组 / 跨组 / 大纲） | 答复人 | 状态  | 结论与依据 | 是否触发变更（级别） | 落实与验证记录 |
| --- | --- | --- | ------- | ----- | ------------ | ------------------ | --- | --- | ----- | ---------- | ------- |

- **谁答复、多快答复**：
  - 只涉及本组的，由本组组长答复；
  - 涉及跨组接口的，由对应接口负责人答复；
  - 涉及大纲规则的，由项目负责人答复；
  - 原则上 2 个工作日内给出答复或处理计划；阻塞开发的疑问当天处理。
- **结论怎么落地**：
  - 结论是"维持原方案"时，把理由补进对应分册，避免同样的疑问反复出现；
  - 结论需要改方案时，按第 11.1 节定级走变更流程。
- **状态取值**：待答复 / 已答复（无需改动）/ 转变更 / 已落实待验证 / 关闭。
  - "已答复"只表示给出了结论；**需要改动的疑问，在改动实施并验证之后才能关闭**。

### 11.5 设计评审的收敛规则（v0.12 起）

- HLD 已经过十余轮全局评审。v0.12 起不再做全局评审：v0.12 的改动（接收时刻证明一期对真实来源禁用、相关机制移出一期）只做一次**定向核对**，范围限于改动部分及其直接依赖。核对没有严重问题即宣布 HLD 收敛、进入实施；此后的修改按第 11.1 节四级变更处理。I4 在 M0 第 1 周末冻结，定向核对须在此之前完成。**执行结果**：四方对 v0.12 的定向核对均结论"可以收敛、无严重问题"，HLD 于 v1.0 收敛；核对提出的登记项已在 v1.0 直接改入（附录 D.1），由两组接口负责人在 M0 第 1 周的 HLD 走读会（第 11.4 节）上确认，按第 11.1 节三级变更的审批口径留痕。
- **严重问题**（出现任一种，修复后再收敛）：
  1. 违反大纲，或扩大、缩小冻结范围；
  2. 可能导致删除后仍可读可写、临时不可用的内容被错误放出，或破坏"不丢不重"承诺；幂等、代次、授权、事务或模式隔离规则被破坏；死锁、锁升级或锁序逆序；
  3. M0 硬判据或任一里程碑出口条目无法判定，或未实现的功能被计作通过；
  4. 改变 M0 第 1、2 周冻结的契约内容，且两组可能按不同理解实现；
  5. 新增大纲之外的状态机或第二套控制协议；
  6. 通俗版的对外承诺错误。
- **其余问题不阻止收敛**：失败方向保守（多禁读、多保持、多回访、多暂停）且只影响 M1 及以后的，登记到第 11.4 节的疑问登记表，写明主责与期限，按本章在 M1 首次联调前关闭，M1 出口评审时逐条复查；无反例的技术偏好或更复杂的防御方案、已有预算 / 主责 / 期限与失败处置的 M1 实现事项、已披露且按大纲保持保守的恢复延迟，也不阻止收敛。
