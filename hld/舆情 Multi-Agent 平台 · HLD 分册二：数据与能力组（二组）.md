## 怎么用这份文档

- **开发以本分册为主**。每个模块按七项组织：交付物、要研究的技术、推荐实现（含为什么这样选）、不要做（含原因）、依赖与接口、测试与验收、必读大纲章节。
- **"必读大纲"是规则规范**。判定条件、状态机、CI 夹具以大纲为准，实现必须逐条满足。本分册不复制这些规则，只告诉你去哪一节看、怎么落地。
  - 每个模块的必读范围 = 总册 §0.2 的**公共必读**（大纲 §2.1–2.4、§4.6、§4.9）∪ 该模块列出的章节。
  - 列表不是豁免：实现中碰到列表以外的规则，照样要读并满足；发现漏项按总册 §11.4 登记。
  - 模块主责维护本模块的"规则—实现—夹具"对照表（总册 §0.2）。
- **"推荐实现"是起点，不是定论**。每条推荐都写了理由。改动按总册 §11.1 定级：
  - 在推荐实现范围内调整细节、在本分册列出的验证候选之间做选择：一级，组内代码评审；
  - 替换推荐方案或引入新的第三方组件，**即使不改跨组接口**：至少二级；
  - 涉及跨组接口或锁约定：三级；触及大纲冻结范围：四级。
- **"不要做"是边界**。每条都写了原因和什么情况下会重新考虑。确有必要时同样走变更流程。
- **有疑问第一时间提**。对推荐或不采用的技术、对理由本身有任何疑问或不同意见，按总册 §11.4 登记，不要带着疑问开发。

## 0. 本组概览

### 0.1 职责

### 0.5 M0 第 1 周技术验证（先验证再开工）

1. **进程组隔离与网络策略**：
   - 每个进程组一个容器（只读根文件系统 + tmpfs + 声明缓存卷），容器内一个监督器；
   - 容器内 cgroup v2 委派：使用私有 cgroup 命名空间；cgroup v2 有"非根组不能既有进程又给子组启用控制器"的规则，监督器要先把自己移到一个叶子组，再在父组启用 memory 控制器、为每个 cpu worker 建子组并设 `memory.max`；
   - 网络默认拒绝，按角色只放行所需内部端点（总册 §2.4）；外网经出口代理，代理按连接器合规清单执行域名白名单。
   - 验证可行，或者给出替代方案。原因：这是底线 2、3 的真正执法点，方案不可行要尽早换。
2. **Jetstream 与 AppView 接口核实**：
   - 锁定所用 Jetstream 协议版本（v1 时间游标 / v2 序号游标）与实例清单；逐项核实大纲 §8.3 列出的帧与错误类型在该版本中的实际名称与语义；超出回看窗口时的实际行为（转入回放流程而不发提示帧时，按游标失效映射，并按总册 §11.1 登记与大纲 §8.3 的差异：差异在总册 §11.4 登记表留痕，第 1 周核实结论给出最终映射）；
   - 账号事件的状态字段（以协议文档为准，例如 `active` 与 `status`）分别映射到永久撤回还是临时原因；
   - AppView 批量查询接口的单次上限（例如 `app.bsky.feed.getPosts` 每次最多 25 个 URI）、公共入口限流与缓存特性，据此估算回访与清扫预算；
   - "追上实时"的判定口径（如何确认已追上实时位点；回放尚未结束时不得确认）；续接游标的语义（续接是否包含与游标相等的事件、上游如何确认接受续接）；是否存在符合大纲 §4.7 第 ⑥ 步的账号控制事件送达保证（按现有官方文档没有：至少一次送达、无时延承诺；结论为没有时 `control_delivery_bound` 按缺省 `unknown`，接收时刻证明禁用，第 3 节）。结论写入 Manifest，随软判据 S2 过夹具。
   - 原因：外部协议可能与大纲描述有出入，越早发现，越早走变更流程。
3. **blob 字节存储方式**：PG 独立表 bytea 或 large object，比较写入、回收、备份行为后选定。
4. **传输服务与 PG 权威令牌桶**：`admit` 短事务的写法（原子判定并扣减）、单机吞吐、内部调用开销与对写入预算的影响；Redis 拒绝镜像的有效期计算（按补充基准与冷却截止）与过期回落。
5. **OTel 关闭载荷采集的配置**：HTTP body、SQL 参数、span 属性中都不得出现原文。
6. **RFC 8785 实现选型**：与一组共同决定。
7. **事务内适配器原型**（与一组联合）：在一组提供的提交上下文中运行，验证不开新连接、不提交、锁层级守卫生效、根来源断言生效。

## 1. 基础设施与开发环境（`adapters/` 与工程底座）

**交付物**

- docker compose 开发环境：PostgreSQL 16 + pgvector、Kafka（KRaft 单节点）、Redis、Jaeger、Prometheus、Grafana。
- `adapters/`：PG 连接池、Kafka 客户端封装、Redis、存储门面基类。
- Alembic 迁移链与 CI 检查；import-linter 配置；CI 流水线骨架（两组共用门禁的执行框架）。

**要研究的技术**

- Kafka KRaft 单节点部署；pgvector 扩展安装；psycopg 3 连接池。
- Alembic 多人协作：分支合并、单链校验。
- import-linter 契约写法（层级、禁止导入）。
- **multixact 监控**：热门账号控制行被大量并发提交取 KEY SHARE 会产生 multixact，看板需展示 multixact 年龄与成员空间，并确认 vacuum 配置能及时回收。

**推荐实现与理由**

- **连接池按用途分开**：普通、控制路径预留、LISTEN/NOTIFY 专用直连。
  - 理由：大纲 §9 要求控制路径预留连接，否则业务高峰时删除与撤回会因为拿不到连接而延迟；LISTEN 需要长连接，不能和普通池混用。
- **存储门面基类内置两个能力**：撤回屏障调用点和删除处理器注册。后续每个存储都继承它。
  - 理由：CI 才能自动检查"有删除处理器的存储，其写入 API 都执行屏障"（底线 4），新加存储时不会忘。
- **Kafka 用 KRaft 单节点**（大纲指定）。
  - 理由：不再需要 ZooKeeper，部署最简单；PG 事件表才是权威，Kafka 单点故障不丢数据。

**不要做**

- 不上 K8s、PgBouncer。原因见 0.6 节。
- 不引入 Elasticsearch / OpenSearch / 图数据库。原因见 0.6 节。

**测试与验收**

- M0：分层 + import-linter + 迁移链进入 CI 门禁。

**必读大纲**：§2.4、§9（PG 资源与写入预算）、§10。

## 2. SDK（`sdk/`）

**交付物**

- **Worker 协议客户端**：对每种提交结局有明确处理表（见下表），与一组的结局枚举一一对应，CI 断言。

| 结局                                | SDK 处理                                                                                                                            |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `receipt`                         | 完成                                                                                                                                |
| `conflict(control_epoch_changed)` | 保留租约，以新前提重算（次数受涉及控制对象数约束）                                                                                                         |
| `conflict(state_version_changed)` | 重读状态后重算，计入预算                                                                                                                      |
| `conflict(lease_lost)`            | 放弃任务（含"检查点版本冲突"诊断）                                                                                                                |
| `conflict(digest_mismatch)`       | 不重试，记录并告警                                                                                                                         |
| `segment_frontier_mismatch`       | 重新 lease                                                                                                                          |
| `retry_after(pg_admission)`       | 指数退避加抖动后重提                                                                                                                        |
| `retry_after(blob_condemned)`     | 按写入方区分：来源正文（normalizer 经 SDK 上传）由 SDK 重新走上传三步生成新实例，再以**同一结果包**重提；统计结果、规则决策由运行时 / 知识服务在计算段之前的"上传准备"阶段重新上传（计算段保持只读），SDK 只做短暂退避后原样重提 |
| `rejected(reason)`                | 不重试，按原因上报                                                                                                                         |

- 另外处理心跳停止指示（代次变更后旧代次任务尽快提交已抓取部分）。
- `handle(tasks: list)` 运行循环（Demo 批大小 1）；结果包组装与 `semantic_bundle_digest` 计算；统一 ID 派生函数。
- 状态 API 客户端（对接一组状态服务 I19）、证据 API 客户端（staged 登记、读取；登记请求带根来源集合）、网关客户端、领域包注入、连接器插件加载器。
- Null / Fake / Real 同工厂的桩化机制；撤回接收与缓存失效钩子（与第 5 节配合）。

**要研究的技术**

- RFC 8785 规范化；asyncio 并发与取消；插件加载（importlib / entry points），并按 `artifact_digest` 校验。
- 指数退避与抖动。

**推荐实现与理由**

- **digest 计算读取 **`contracts/`** 中的字段元数据**（include / exclude），SDK 自身不写字段清单。
  - 理由：字段清单只有一份，契约改了 SDK 自动跟上，不会出现两边摘要算法不一致导致回执幂等失效。
- **ID 派生**：`H(task_id, segment_no, output_kind, local_output_index)`。
  - 理由：同段重传得到同样的 ID，重试天然幂等；不同段、不同对象类型不碰撞（大纲 §4.7）。
- **结局处理表与一组枚举一一对应，CI 断言**。
  - 理由：新增结局时，如果 SDK 没处理，CI 直接失败，不会在运行时才暴露成"任务卡死"。
- `retry_after(blob_condemned)`** 以同一结果包重提，重传由该种类的写入方负责**。
  - 理由：逻辑证据身份不含实例 ID，重传生成新实例后结果包摘要不变，回执幂等仍然成立（大纲 §4.3）；提交事务内首次创建的种类只有来源正文、统计结果、规则决策三种，后两种的字节不在 SDK 手里，SDK 只能退避后重提，由运行时 / 知识服务在上传准备阶段重传（分册一 §3）。上传期间不持任务行或控制对象行锁。
- **插件加载时校验制品摘要与合规清单版本**，不匹配拒绝启动。
  - 理由：保证运行的就是登记过的那个连接器版本（大纲 §5 连接器质量门槛）。

**不要做**

- SDK 不依赖 `runtime/`。原因：SDK 跑在 worker 进程里，依赖 runtime 就会把运行时代码和权限带进 worker，违反分层（大纲 §2.4）。
- 不在 SDK 内做"权威校验"。原因：worker 端不可信，权威校验在运行时侧重算并签名；SDK 可以做预检查帮开发者早发现问题，但结果不被信任。
- 不向 worker 下发数据库凭据。原因：底线 3，状态归平台管理。
- `digest_mismatch` 与 `rejected` 不重试。原因：同任务不同摘要说明结果包本身有问题，重试只会重复失败。

**依赖与接口**

- 一组：Worker 协议服务端（I1）、状态服务（I19）与契约元数据。

**测试与验收**

- M0：并发与重复 complete 同回执（客户端重试行为）；worker OOM 重派无重复（与第 5 节）；`retry_after(blob_condemned)` 重传后同包重提成功（与一组联合）。

**必读大纲**：§2.3、§2.4、§4.3（上传三步、`retry_after(blob_condemned)`）、§4.4（Manifest）、§4.7（Worker 协议、ID 派生、digest、分段收口、提交结局）。

## 3. 受控传输层与限流准入

**交付物**

- SDK 内的 HTTP 与 WebSocket 句柄（I4），绑定执行上下文、凭据范围、预算。连接器进程不访问 PG、Redis，下面三件事都经**传输服务**（第 4 节）完成。
- **令牌桶准入**（`rate_scope` 按凭据 / 按主机）：
  - 令牌余额、补充基准与冷却记录的权威在 PG；
  - 每次外部请求前，受控传输层调用传输服务 `admit(rate_scope, cost)`；传输服务用一个 PG 短事务原子地判定并扣减，返回许可后才访问网络；
  - Redis 只作**带有效期的拒绝镜像**：零余额镜像的有效期不超过按补充基准算出的下一次可能取得令牌的时点，冷却拒绝的有效期不超过冷却截止时点；
  - 镜像过期、缺失（Redis 丢失或重启）或无法确定有效期时视为未知，照常回到 PG 准入，并以 PG 当前记录重建镜像；Redis 显示有额度时也不能直接授权；
  - Redis 丢失或回退既不能恢复出额外额度，也不能让采集永久停摆。
- Retry-After 与 429 冷却经传输服务 `report_throttle` 持久化；出站审计与计量；传输重试与作业重试共用预算。
- **账号控制事件的接收记录**（一期用于审计与夹具；接收时刻证明的启用范围见本段末，大纲 §4.7 第 ⑥ 步、§9）：
  - **实时连接登记**：实时入口建立连接之前，SDK 经传输服务登记该连接（来源、作业、`process_instance_id`），取得连接编号，并得到**本作业是否为该来源当前的权威作业及指定版本**（位置模式来源，见下）；登记成功之后才开始订阅接收。登记失败或超时按退避重试，期间不启动该连接；已在运行的连接不受影响；
  - 受控传输层在每个响应或帧到达时打接收时间戳（墙钟）并按到达顺序编帧序号。传输层看不懂帧的含义，所以由**连接器**在解析出账号控制事件后，**立即**经受控传输句柄调用 `record_receipt(帧引用, 上游事件身份)`；**接收时间戳、入口、连接与追赶标记由 SDK 按帧引用附加，连接器不能填写或修改时间**。传输服务以独立短事务写入接收记录，只增不改，按（连接，帧序号）幂等；不等 staged 登记，任务后来被取消也不影响它。事件在接收记录确认（或放弃重试）之后才进入 FetchPage；
  - **首次接收时刻**：某事件的首次接收时刻取该事件全部接收记录中最早的接收时刻，连同该记录的追赶标记一起返回；重试、重收、补偿只会增加记录，不使首次接收时刻后移。`ON CONFLICT DO NOTHING` 只用于同一连接同一帧的重复登记去重，"取最早"由查询完成；
  - **追赶标记**：断线重连、游标回放、resync 补采、实例切换衔接期间接收的帧带追赶标记，连接器确认追上实时位点后清除；无法确认时整段按追赶处理。追赶标记与接收时刻一并持久保存（大纲 §9）；
  - `record_receipt` 失败或超时**不阻塞采集**：先按同一（连接，帧序号）重试，确认丢失时重试返回原结果；放弃重试时该事件按"未登记"进入采集结果包，照常进入控制信号路径。传输服务不可用期间，已在运行的连接继续接收、不因登记失败断开；恢复后在同一连接上继续登记，中断区间（起止帧序号与时刻）记入审计。没有接收记录的事件不补造首次接收时刻；
  - **权威作业指定**（位置模式来源，总册 §6.8）：来源配置必须指定一个作业为该来源的**权威作业**，不以"连在权威实例上"自动认定。指定记在**来源一级**，由传输服务统一保存，写入只经传输服务的权威作业指定写入接口（I4），只接受运维身份调用：首次指定随来源配置发布、改指定按下面的运维步骤，都由运维工具提交，每次写入记录操作人与依据，生成新的指定版本号；同一来源任一时刻至多一个权威作业；**不按各作业各自钉定的执行配置锁分别解释**。只有第 ⑥ 步执行时的权威作业，其显式切换报告或接任报告才能移动权威位置域；其他作业的显式切换报告按非权威域处理并告警，不建立 handoff。改指定到另一作业后，新作业带**接任报告**（第 7 节），由一组在第 ⑥ 步决定是否建立 handoff（总册 §6.8）。第 ⑥ 步经 I7 的**即时授权查询**判定，按查询语句执行时已提交的最新指定版本，不需要生效时刻（总册 §6.8 第 2 步）。改指定的运维步骤：经运维工具只读查到来源控制行记下的**建立依据作业**及其检查点中该域的最后已处理位置 → 让新权威作业以该位点订阅成功 → 经运维工具调用传输服务的权威作业指定写入接口登记新指定 → 新作业重建实时连接（登记时得到新指定版本，据此带接任报告）。同域续接不上时，一组在第 ⑥ 步按接任空档处置在同一次提交内设置门控、暂停作业，本组负责其后的核验与解除（总册 §6.8 第 2 步）；
  - **接收时刻证明一期只对夹具来源开放**：
    - 夹具来源指连接器为 http-fixture 的来源，只在测试环境运行，控制效果按既有模式隔离。它的 `control_delivery_bound` 可以声明合格的 guarantee，用来承载大纲 §8.3 Bluesky 行列出的接收时刻证明夹具（总册附录 C 的 M1-8.5b）；这是受控的测试前提，不代表 Bluesky 有送达保证。声明合格 guarantee 的夹具配置只用于接收时刻证明的判定例；其余夹具——包括接收记录夹具中的登记中断场景，以及比较基准、保守保持与回访、交接核对各组——一律用送达上界 `unknown` 的配置运行，与 Bluesky 一致，测的是生产实际走的"保持 + 回访"路径。判定例只用单一实时连接、不含登记中断，事件在接收记录确认后才进入 FetchPage，所以证明使用首次接收时刻时，该事件的记录已经齐全（多入口、登记中断后上游重送等情形下的可证明性属于下面的前置条件）；
    - **能力闸门**：计划解析时，非夹具来源的 `control_delivery_bound.kind` 为 guarantee 的一律拒绝（同大纲"`worker_checkpoint=false` 时拒绝长会话"的做法），不做静默降级。`control_delivery_bound` 按大纲 §4.4 在连接器 Manifest 中声明（缺省 `unknown`），来源配置可以覆盖；能力闸门只看执行配置锁里合并后的有效值，来源配置的任何新版本进入执行配置锁之前都过同一检查。真实来源按缺省 `unknown` 处理，接收时刻证明禁用；Bluesky 的 Manifest 写明 `unknown` 与 M0 第 1 周的核实结论（0.5 节第 2 项）；
    - 禁用只去掉这一种证明方式：其他有效证明（如时间模式下的可信事件时间证明）、正常的有序清除与既有保持规则照常；原本需要这种证明、又不能经其他途径证明的清除，登记或并入保守保持、经回访生效（大纲 §4.7 第 ⑥ 步），**不得把"未启用"当成"无需证明"而按比较键直接清除**；
    - 启用时（一期只有夹具来源）：一组提交路径按上游事件身份经 I7 查询首次接收时刻与追赶标记，不读结果包中的时间字段；首次接收带追赶标记或查不到记录的，该证明不通过；
  - **对真实来源启用的前置条件（一期不实现）**：真实来源取得符合大纲 §4.7 第 ⑥ 步的送达保证只是必要条件。启用前还须按总册第 11 章三级变更先实现并验收下列机制，再放开能力闸门。这些机制在 v0.11 文档中有完整写法，恢复时以它为起点重新评审：
    - 首次资格判定：只有来源级指定的资格入口（位置模式下即权威作业）的记录可能有资格；同一入口单一活动会话（会话重叠为否）；登记延迟上界；会话先于接收、同一会话按序号串行登记与会话完整性；只判定最早一条记录，并须确认相关入口的会话登记完整，不能把未确认的入口视为不存在；
    - 订阅范围级"首次资格待证明"与未解除的不完整会话责任集合，指定变更时的责任继承；
    - 追赶状态报告、会话终止确认查询、上游实例身份与同实例会话轮换；登记中断后的资格恢复；
    - 指定版本的生效时刻（取数据库提交时间戳，需开启 PG 的 `track_commit_timestamp`）、观测登记时的指定版本前沿、墙钟偏差带，以及按接收时刻的历史查询；
    - CI 断言：任何已经对外使用过的首次接收时刻，都不会因为随后出现更早的记录而需要向前修正；
    - 核实来源协议"同一上游实例按位点顺序只实时送出每个事件一次"。按现有官方文档，Jetstream 为至少一次送达、实例重启后会重送，这一条目前不成立。

**要研究的技术**

- 令牌桶算法；PG 短事务的原子扣减写法（条件更新或行锁）；HTTP 条件请求与缓存头。
- WebSocket 重连、心跳与背压。
- 时间来源：持久化用墙钟并监控主机间时钟偏差，超时计算用单调时钟。

**推荐实现与理由**

- **所有网络访问集中在传输层**，连接器只拿到受控句柄。
  - 理由：限流、冷却、网络策略、审计、计量、接收时刻这些都只需实现一次；连接器开发者不可能"忘了"做其中某一项（大纲 §8.2）。
- **令牌以 PG 为准，准入先于网络访问**。
  - 理由：额度是对外部平台的承诺，多发一次就可能触发对方封禁；只有 PG 短事务能在崩溃、重启、Redis 丢失时都保证不超发。代价是每次请求多一次内部调用和一次短事务，计入写入预算（总册 §12）。
- **Redis 拒绝镜像必须会过期**。
  - 理由：零余额镜像如果没有失效条件，PG 那边补充出新令牌后，请求仍被 Redis 挡住、进不了 PG 准入，镜像也就永远不会被更新，采集会一直停摆。
- **接收时刻在收到的那一刻登记，取全部记录中最早的一条**。
  - 理由：如果用入库或处理时刻，平台内部排队的时间会被算进去，导致把旧事件误判为新事件（大纲 §4.7 第 ⑥ 步）。"先落库"不等于"先接收"：入口 A 在 100 收到但登记延迟、入口 B 在 130 重收却先登记时，按落库先后会把 130 当成首次。要在多入口、登记延迟、会话中断时都能证明"这就是平台首次接收"，需要本节列出的整套前置机制。
- **一期接收时刻证明对真实来源缺省禁用，只对夹具来源开放**。
  - 理由：大纲要求送达上界是覆盖账号控制事件、端点到本平台首次接收的 guarantee，不满足即禁用；Jetstream 官方文档没有这种保证（至少一次送达、无时延承诺）。为一期不能启用的路径实现整套资格保护不划算；禁用的代价是部分账号恢复要等一次回访（总册第 13 章）。能力闸门防止有人只改配置、在缺少前置机制的情况下启用。
- **追赶标记**：重连或回放开始时置位，连接器确认追上实时位点后清除；无法确认时整段按追赶处理。
  - 理由：追赶期间收到的事件实际发生得早得多，来源声明的实时送达上界在这段时间不成立，不能用来证明时间先后。
- `control_delivery_bound`** 的取值要把主机间墙钟偏差计入**；主机墙钟偏差上界登记在来源配置中，随执行配置锁版本化。
  - 理由：接收时刻用传输主机的墙钟记录，参照时刻可能来自其他主机；偏差不计入，证明会偏松。
- **时间来源**：持久化用墙钟，超时计算用单调时钟。
  - 理由：墙钟可能被校时调整，用来算超时会出错；持久化的时间又必须是墙钟才能和其他记录比较。

**不要做**

- 网络等待期间不持有数据库连接。原因：大纲 §3.3 明确要求；否则慢接口会耗尽连接池。准入短事务在访问网络之前提交。
- 不向连接器暴露原始 socket 或底层客户端。原因：一旦暴露，就能绕过上面所有控制。
- 不以 Redis 为令牌权威。原因见 0.4 节。

**依赖与接口**

- 提供：受控传输句柄与传输服务（I4，本组连接器使用）；首次接收时刻与追赶标记（经 I7 供一组查询，只在启用接收时刻证明的来源上使用）；权威作业指定的即时授权查询（经 I7）。

**测试与验收**

- M0：夹具 429（无前缀）→ 冷却 → 恢复，检查点不推进；有前缀时只推进前缀（与一组决策表联合）。
- 令牌桶夹具：Redis 清空或回退后，总发放额度不超过 PG 记录；并发请求不超发；零余额后推进时间、不修改 Redis，请求最终回到 PG 并恢复、恢复过程中不超发；Redis 清空后采集自行恢复，不超发、不停摆；连接器进程直连 PG / Redis 失败。
- 接收记录夹具（总册附录 C 的 M1-8.5a）：重试 / 重收 / 补偿不使首次接收时刻后移（同一事件的两条记录反向完成登记、较晚记录先可见，两条都提交后查询返回较早那条）；连接器传入时间被拒；同一（连接，帧序号）重复登记幂等，确认丢失后重试返回原结果；追赶标记在重连、回放时置位，确认追上实时后清除，无法确认时整段按追赶；登记失败不阻塞采集，该事件按"未登记"进入结果包；传输服务停 2 分钟期间已在运行的连接持续接收，恢复后在同一连接上继续登记，中断区间记入审计；实时连接登记返回是否为当前权威作业及指定版本，登记成功前不订阅；改指定后新作业重建连接，得到新指定版本。
- 能力闸门（与一组联合，总册附录 C 的 M1-8.5b）：非夹具来源在 Manifest 或来源配置任一处声明 guarantee、合并后有效值为 guarantee 时计划解析拒绝；Bluesky 来源按 `unknown` 通过计划解析、接收时刻证明禁用。

**必读大纲**：§3.3（受控传输层）、§4.7 第 ⑥ 步（接收时刻证明，理解其输入要求）、§4.11（决策表第 9–12 行：限流与传输错误）、§8.2、§8.4（`rate_scope`）。

## 4. 运行时外围

**交付物**

- **定时表**：周期计时器、冷却恢复计时器（绑定冷却代次或触发 PageResult）、连接计时器、回访与核验预算的退避计时器、**保持回访计时器**（带 hold\_id）。
- **定时表事务内登记（I21）**：事务内适配器，供一组提交段在**第 ⑨ 步**登记决策表计时器与保持回访计时器（第 ⑥ 步只生成意图），以及 I16 按控制状态转换函数的输出登记计时器。回访计时器属于随控制结果产生的写入，不属于调用方的清理类明确操作；不得仅因调用方传入登记请求而执行。目标已达成且本次转换未产生计时器意图时，不登记计时器。状态行层级（总册 §7.4.1）。
- **定时服务**：到期后只调用一组任务创建 API（I2）新建任务；回访计时器到期即在独立事务中经 I2 创建回访任务。
- **注册中心与版本对账**：Registry 版本对账为真相，LISTEN/NOTIFY 走专用直连会话，只用于加速。
- **执行上下文装配**：平台构造，Agent 不可伪造，Manifest 不能自行扩大权限。
- 配额。
- **传输服务**（与配额同一模块，平台服务，持有 PG 连接）：受控传输的平台侧服务端，提供 `admit(rate_scope, cost)`、`report_throttle(rate_scope, retry_after)`、`record_receipt(...)` 三个网络 API，并维护 Redis 拒绝镜像、实时连接登记与来源级的权威作业指定（写入接口只接受运维身份调用，每次改指定生成新的指定版本号并记录操作人与依据；行为见第 3 节）。M0 第 3 周交付 `admit` 与 `report_throttle`，第 4 周交付 `record_receipt` 与实时连接登记。
- **撤回接收登记服务**（平台服务，与定时服务同一部署，持有 PG 连接）：worker 与监督器向平台登记撤回接收状态的入口，提供 `register_process(process_instance_id, 进程组身份, start_frontier)`、`report_frontier(process_instance_id, seq)`、`report_retired(process_instance_id, 依据)`、`list_unretired(进程组身份)` 四个网络 API，写入进程前沿表；进程组身份是容器重启前后保持不变的标识（例如进程组名 + 副本序号）；`report_retired` 只供监督器（或第 5 节的运维工具）在"cgroup 终止 + 缓存已清空"后调用，调用方须为监督器身份或运维身份，服务端按身份校验依据取值，依据取值含"进程已终止并清空缓存""容器重启后核对""运维核对"，`list_unretired` 供容器重启后的新监督器与运维工具查询未退役进程实例；收到 `report_retired` 即结束该进程在传输服务登记的全部会话（记为"不完整"，除非已正常关闭）。**M0 第 3 周先交付登记 API 的 Fake**（遵守桩化标识，供集成点 1 的进程注册；SDK 仍须收到注册成功才领取，不得绕过注册检查），**第 4 周交付真实服务**，接入后重新执行注册失败不领取、前沿回报与退役夹具；M0 硬出口不使用 Fake 登记结果作证据（总册 §8.2）。
- **凭据代理 Fake 与鉴权身份源桩**：身份源桩只桩"身份从哪里来"，**不得桩掉证据写入方鉴权、租户检查与模式检查**。

**要研究的技术**

- 基于 PG 的定时任务表（到期扫描 + `SKIP LOCKED`）；PostgreSQL LISTEN/NOTIFY 的可靠性边界（通知可能丢失，必须以对账为准）。

**推荐实现与理由**

- **计时器存在 PG 表里**，每行带稳定身份（周期身份、冷却代次、恢复身份、hold\_id），重复触发幂等。
  - 理由：计时器和任务、作业在同一个数据库里，崩溃重启后不丢；稳定身份保证旧计时器不会误触发（大纲 §4.11）。
- **到期后只调用一组的任务创建 API 新建任务**，不直接插任务行。
  - 理由：该 API 在作业行锁内复核代次与栅栏，保证代次变更期间不会冒出旧代次任务；计时器自己插行就会绕过这道检查。
- **回访经计时器建任务，不在提交事务里建**。
  - 理由：一组提交段第 ⑥ 步不能经任务创建 API 取作业行锁（锁序冲突）；"立即到期计时器 + 定时服务独立事务建任务"把两件事拆开（总册 §6.7）。
- **以对账为准，NOTIFY 只用来加速**。
  - 理由：NOTIFY 在连接断开等情况下会丢，只靠它会漏掉注册变更。

**不要做**

- 计时器不直接使在途任务失效。原因：会与在途提交竞争，应由提交时的 CAS 统一拦截。
- 计时器事务不持作业锁再获取锁序中更靠前的行。原因：违反全局锁序（大纲 §4.7）。
- 不以 NOTIFY 作为唯一触发源。原因见上。

**依赖与接口**

- 依赖：一组任务创建 API（I2）。
- 提供：I21。

**测试与验收**

- M0：cooling 期间计时器在栅栏之后到期，不新建任务（与一组代次变更夹具联合，H15.10）。
- M1：保持回访计时器到期后恰好创建一个回访任务（与一组联合）；I16 目标已达成时不登记回访计时器，新建保持时按转换函数输出登记（与一组联合，总册附录 C 的 M1-D9.5）。

**必读大纲**：§3.2（集中分发、Registry 对账）、§4.6（执行上下文）、§4.7（全局加锁顺序）、§4.11（作业状态机中计时器相关部分、代次变更协议对新建路径的要求）。

## 5. worker 进程组、网络策略与监督器

**交付物**

- 四类资源：io 池（asyncio，独立进程组）、cpu 池（每 worker 独立 OS 进程，spawn，BLAS 线程 = 1）、llm 池（经网关）、PG。
- 按连接器制品摘要划分的连接器进程组（collector + 连接器）：网络策略与凭据按进程组下发；升级时新组拉起、旧组排空；启动崩溃循环退避与熔断。
- 按连接器制品摘要划分的 normalizer 进程组框架：每个进程只加载一个连接器制品（总册 §7.4.2），无外网；规范化任务按其携带的连接器制品摘要路由，连接器升级时旧组在其规范化任务全部完成之前不退役。
- **网络策略**：默认拒绝，按角色只放行所需端点（总册 §2.4 网络策略表）。Agent 的模型请求只能发往网关；连接器进程不访问 PG、Redis，令牌准入、冷却登记、实时连接登记、接收记录登记经传输服务完成，外部访问只经受控传输 → 出口代理，按合规清单域名白名单；证据服务、知识服务、网关、传输服务作为平台数据服务可访问 PG。
- **监督器**（每个进程组容器 1 个；持有内容派生进程内缓存的平台服务容器，如知识服务，也各 1 个）：
  - 绑定 task / lease / 墙钟 / 进程；
  - cgroup 内存与墙钟超限即终止，经 fencing fail 结算；
  - 有限重试后进死信或暂停；
  - 健康探测走独立控制通道；
  - **容器重启后**，新监督器经 `list_unretired(进程组身份)` 查得前任进程实例，先核对它们已不存在、声明的缓存卷已清空，再逐个提交 `report_retired`；只有缓存卷不可达、无法核对时，前任进程才记为"待核验副本"；
  - **进程组缩容或宿主机永久丢失**、不会再有新监督器以该身份启动时，由运维工具按同一流程处理：`list_unretired(该进程组身份)` → 核对进程已不存在、缓存卷已销毁 → `report_retired`（依据为"运维核对"）；缓存卷无法核对的记"待核验副本"。运维工具需要与监督器同等的核对权限，但使用单独的运维身份（与监督器身份分开，总册 §2.4 网络策略），每次 `report_retired` 记录操作人、依据与核对证据。
- 文件系统只读（例外：有上限、重启即清空的 tmpfs；声明的缓存目录）；设置 `PYTHONDONTWRITEBYTECODE`。
- **撤回接收端**（I8 接收端）：
  - 唤醒信号（LISTEN/NOTIFY 或外发箱事件）只表示"有新撤回"；接收端经运行时 API `withdrawals_since(seq)` 按序号从 PG 拉取，**发现空洞先补齐**，确认连续后才推进并回报"连续已处理前沿"（键为 `process_instance_id`）；
  - `register_process`** 成功之前，SDK 不调用 **`lease`**、不启用缓存钩子**；注册失败时按退避重试，重试期间不接任务；
  - 前沿回报经撤回接收登记服务 `report_frontier`；worker 不访问 PG；
  - 收到撤回后在有界时限内剔除或重建缓存；
  - 进程启动或重新注册前先清空缓存，再以当时的撤回日志前沿与所在进程组身份经 `register_process` 注册；
  - 心跳失联的进程，经监督器可验证销毁（cgroup 终止 + 缓存目录清空）并调用 `report_retired` 后才移出清理等待集合；监督器所在容器整体消失、无法提交退役确认时，该进程记为"待核验副本"。
- **缓存临界区与填充屏障**（worker 进程内的缓存不取数据库锁）：
  - 缓存的计算可以在临界区之外进行（不含模型调用、抓取、无界重建）；
  - **最终发布**与**撤回应用、连续前沿推进**必须经过同一个缓存临界区；
  - 填充前记录当时的撤回前沿 f0；发布前在临界区内**只用本地已拉取的撤回日志**（f0 之后的条目）复核新条目，命中即剔除，然后才使条目可见；**临界区内不发网络请求**，以免撤回应用与前沿推进被网络耗时拖住；
  - 临时不可用不进入撤回日志，按读时门控处理：worker 使用缓存内容时，经证据服务提供的可用性查询（I17 的查询形态，可按批）过滤；
  - 撤回处理器在剔除完成之前不得推进前沿；
  - 理由：否则可能出现"复核完、尚未发布时撤回到达并推进了前沿，随后旧条目被发布"的复活。

**要研究的技术**

- Python multiprocessing spawn 模式；cgroup v2（`memory.max`、进程归组、整组 kill、容器内委派与"无内部进程"规则）。
- 容器只读根文件系统与 tmpfs；容器网络隔离、默认拒绝策略与出口代理域名白名单。

**推荐实现与理由**（按 0.5 节的验证结果定稿）

- **每个进程组一个容器**，容器内一个监督器为 cpu worker 建 cgroup 子组。
  - 理由：容器天然提供只读根文件系统、tmpfs、网络隔离；cgroup 子组让单个 worker 超内存时只杀它自己，不影响同组其他 worker。
- **网络执法放在进程组级，默认拒绝、按角色放行**。import-linter 只是辅助手段。
  - 理由：大纲 §2.2 底线 2 明确"真正执法是进程组级网络策略"；代码层的约束挡得住误用，挡不住绕过。按角色放行而不是"只放行网关"，Agent 才能访问运行时、证据服务和知识服务。
- **cpu worker 设 BLAS 线程 = 1**。
  - 理由：numpy 等库默认会开多线程，多个 worker 进程叠加后会严重超额占用 CPU，反而变慢。
- **撤回以 PG 日志为准，广播只唤醒**。
  - 理由：消息可能丢失；只有能按序号补齐，"连续已处理前沿"才可信（大纲 §3.3）。
- **回报"连续已处理前沿"，不是"收到的最大序号"**。
  - 理由：只有连续处理到某个序号，才能证明之前所有撤回都已生效；收到 10 号不代表 5 号已处理。

**不要做**

- worker 不持有数据库凭据。原因：底线 3。
- 不靠代码约定代替网络执法。原因见上。
- 不在没补齐空洞时推进前沿。原因见上。

**依赖与接口**

- 依赖一组：撤回日志发布与 `withdrawals_since(seq)`（I8）。

**测试与验收**

- **M0**：worker OOM 重派无重复；网络策略按角色放行的夹具（Agent 进程访问网关、运行时、证据服务成功，访问外网失败；连接器进程访问白名单外域名失败）；进程 A 已处理高序号而进程 B 丢失低序号消息时不判定完成。
- **M1**：进程活着但心跳断开、退出后缓存目录仍存在、旧进程恢复，三种夹具下都不宣布全副本清理完成，读取仍立即禁用；容器重启后新监督器经 `list_unretired` 查得前任进程、核对后退役，不永久滞留。
- **M2**（故障注入中的进程组子项）：缩容一个进程组后，运维工具经 `list_unretired` 核对并退役该身份登记过的进程，清理完成判据可以达到。

**必读大纲**：§2.2（底线 2、3、6、7）、§3.3（撤回控制通道）、§5（连接器进程隔离）、§9（四类资源）。

## 6. 采集：collector 与连接器框架

**交付物**

- collector Agent（io 池）：按作业调用连接器 `fetch(job, checkpoint, budget, transport)`，组装 FetchPage 结果包并提交。
- 连接器 SPI 框架：`auth / fetch / normalize / health`。
- **FetchPage 线解码分层**（与一组第 1 节的契约一致）：线解码检查结构、必填与基本类型，**枚举类字段以字符串接收并保留未知值**，交给违规清单分类；不静默丢字段、不做会改变摘要的类型转换；SDK 组装与输出用的构造模型可以用严格枚举。
- 原始响应 staged 登记：在 complete 之前，以独立事务经证据 API（I6）登记，请求带根来源集合；根来源由证据服务按证据身份与父证据推导，请求中带的集合只用于核对，不一致即拒绝；该事务按任务行 `FOR UPDATE` → 根来源控制行 KEY SHARE → blob 行 → 逻辑对象行加锁，复核任务非终态、当前租约与永久撤回。账号控制事件的接收记录已在收到时经传输服务登记（第 3 节），不在这里写。
- 边缘过滤与跟踪集合：
  - 跟踪集合 = 正式对象 + staged 对象 + 本批次已选对象；
  - 同切片内 create 后 delete 按原生顺序折叠；
  - 删除事件按键控哈希身份查找。
- revisit 调度（渐长间隔）；评论树子作业（余力）。
- 采集看板（Grafana + 列表页）。
- 每个来源的合规清单：endpoint、权限范围、许可用途、保留期、模型处理与展示许可、删除时限、核验依据与时效。
- 连接器质量门槛：合规清单审批并绑定版本、存量原始响应 normalize 回归、状态映射夹具、检查点兼容性。
- **采集入口限速执行点**（M2）：阀门策略由一组定义，本组在采集入口执行并留痕。

**要研究的技术**

- FetchPage 字段语义：status、completeness、end\_reason、item\_outcomes、tombstones、control\_events。
- 有界任务：请求数 / 消息数 / 解压字节 / 耗时 / 页数上限。
- 抽样口径区分：概率抽样、配额抽样、接口截断。

**推荐实现与理由**

- **连接器只报告观测事实，下一步动作由一组的决策表决定**。
  - 理由：各平台接口千差万别，让每个连接器自己决定"失败了怎么办"会让系统行为无法预测；集中到决策表后行为一致，可以穷举测试（大纲 §4.11）。
- **未知枚举值不在解码阶段拒绝**。
  - 理由：大纲违规清单 V1 要求未知枚举值进入违规分类，走受限投影保住墓碑；在解码阶段报错就绕过了这条路径。
- **原始响应在 complete 之前单独登记**。
  - 理由：原始数据先可靠落库，后续处理崩溃也能从原始数据重做；登记事务先锁任务行，避免任务已经结束还挂上无人负责的持有（风险 R41）。
- **每个连接器配一套"状态映射夹具"**：把来源的各种响应映射成 FetchPage，确保不触发违规清单。
  - 理由：外部接口的边界情况（限流、半页失败、游标过期）平时很难遇到，靠夹具固定下来才能回归。
- **跟踪集合包含 staged 对象和本批次已选对象**。
  - 理由：帖子刚采到还没转正就被删除时，删除事件也必须能找到它，否则会漏删。
- **revisit 节奏可配置，但不作调节阀**。
  - 理由：revisit 决定删除被发现的速度，压缩它会直接拉长删除探测时延（风险 R24）。
- **纯删除切片照常提交**：内容条目为空或全部已被撤回时，控制信号、PageResult、覆盖声明与检查点仍正常提交（一组分册一 §3 的采集包规则）。

**不要做**

- 连接器不自建网络客户端。原因见 0.6 节。
- 连接器不决定重试或暂停策略。原因见上。
- 不在 normalize 中产生墓碑。原因：删除信号只有一条正式路径（fetch 阶段放进 `tombstones[]`），多路径会造成重复或冲突（大纲 §4.12）。

**依赖与接口**

- 依赖一组：FetchPage 契约与决策表（I3）、任务创建 API（I2）；normalizer 调用本组的 `normalize()`（I15）。

**测试与验收**

- **M0**：SPI、collector、file / fixture 连接器、进程组隔离。
- 解码夹具（与一组联合）：未知 status 但墓碑有效的包进入违规分类且墓碑经受限投影登记；结构损坏的包在解码层拒绝。
- **M1**：真实来源端到端；一页中崩溃可恢复（与一组联合）。

**必读大纲**：§4.3（staged 登记与写入方）、§4.7.2（采集提交）、§4.11（FetchPage、多资源页条目结果、边缘过滤、有界任务、fetch\_mode、抽样区分、违规清单）、§5（连接器清单与质量门槛）、§8（采集框架全章）。

## 7. 连接器：bluesky-jetstream（含公开 AppView）

**交付物**

- 增量：Jetstream WebSocket 订阅。commit.create / update 产生原始条目；commit.delete 产生 `tombstones[]`；账号事件产生账号控制信号；identity 产生身份变更记录。
- 核验：AppView 批量查询，用于 revisit、sync 之后的账号批量核验、resync 清扫。
- 协议锁定（M0 软判据）：endpoint、协议版本、游标解释、保留与续接能力写进 Manifest 并过夹具；"追上实时"的判定口径（如何确认已追上实时位点；回放尚未结束时不得确认）、超出回看窗口时的实际行为（转入回放而不发提示帧时按游标失效映射，按总册 §11.1 登记差异），以及有无符合大纲的账号控制事件送达保证的核实结论，同样写进 Manifest，随软判据过夹具（0.5 节第 2 项）。
- 来源配置：`comparison_basis`、上游事件时钟偏差上界、`verification_basis`；`control_delivery_bound` 在连接器 Manifest 中声明、来源配置可覆盖，能力闸门看合并后的有效值（Bluesky 按缺省 `unknown`，接收时刻证明禁用，第 3 节）；权威作业为来源级指定，由传输服务按指定版本号保存，不随各作业的执行配置锁分别解释（第 3 节）。

**要研究的技术**

- AT Protocol 基础：DID、handle、`at://` URI、record 与 collection（如 `app.bsky.feed.post`）。
- Jetstream：WebSocket 订阅、按 collection / DID 过滤、cursor 语义、事件类型（commit / identity / account）。
- **账号事件的状态映射**：以协议文档为准（例如 `active` 与 `status` 字段），账号删除映射为永久撤回；停用、暂停等映射为 `account_inactive`；含义有歧义的取值登记差异，按变更流程确定映射。
- 公开 AppView 的 XRPC 接口：例如 `app.bsky.feed.getPosts` 按 URI 批量查询（单次上限例如 25 个 URI）、`app.bsky.feed.getPostThread`、`app.bsky.actor.getProfile`。要研究它们的缓存行为、公共入口限流，以及如何给出新鲜性下界。
- Bluesky 开发者条款与数据使用合规。

**推荐实现与理由**

- **增量走 Jetstream，核验走 AppView**。
  - 理由：Jetstream 推送 JSON 格式的增量事件，省去解析原始 firehose 的复杂度，适合持续采集；AppView 支持按 URI 批量查询，适合回访与核验。两者分工也对应大纲"增量路径 + 存在观测路径"两条核验路径。
- **批量按 URI 查询属于"按条目寻址"**：请求了却没返回的条目记 `missing`，按缺失观测规则计数。
  - 理由：大纲 §4.11 只允许按条目寻址的请求报告 missing；按查询或列表的请求只能报 present。
- **回访与清扫预算按批量上限与公共限流估算**，写入来源配置。
  - 理由：清扫速度直接决定断流后多久能恢复可读、删除多久能被确认。
- **游标推进基于已持久化的连续前缀**。
  - 理由：崩溃后从游标续接时，不会跳过还没落库的事件。
- **过滤订阅造成的 seq 跳跃，不套用内部 causal 缺口检查**。
  - 理由：按 collection / DID 过滤后，seq 本来就不连续，套用缺口检查会误报。
- **实例切换必须显式报告**：连接器按大纲 §4.11 在覆盖信息与位点中报告本包所在的位置域（上游实例标识）和排序域；**实时连接切换实例时，显式报告"本作业的实时连接从位置域 X 切换到 Y"**，附 X 的最后已处理位置、Y 的起始位置与位点映射验证结果；非切换的包只报告所在位置域。一组只在收到**权威作业**的显式切换报告或接任报告时登记 handoff\_epoch（总册 §6.8）。**两种报告都按检查点判断、重复携带**：每个包比较检查点记下的位置域与本包所在位置域，不同时带显式切换报告（旧域最后已处理位置取自检查点）；比较实时连接登记返回的权威作业指定版本与检查点记下的版本，本作业新成为权威作业、检查点里还没有该版本时带接任报告，报告中的**连续接收起点**取检查点记下的值：本作业在该位置域内，自最近一次连续性中断以来向上游请求续接、并被上游接受的起始游标——**不是第一条收到的事件的位点**。游标失效后的 resync 或检查点迁移、事前审批的强制跳过、作业代次变更中不能逐位对应的检查点迁移、实时连接切换位置域，都算连续性中断，起点改为中断后实际续接的游标；上游对续接游标给出过期类提示的按游标失效处理（大纲 §8.3），不作为起点；没有检查点时取本会话请求并被接受的起始游标。连接器要保存"请求并被接受的游标"；续接语义（是否包含与游标相等的事件）写进 Manifest，随软判据 S2 过夹具；过滤订阅造成的位点跳跃不算空档。带报告的包以正常结局提交时，无论位点是否推进，检查点都记下本包的位置域、指定版本与连续接收起点；违规结局与未提交的包不记，报告随后续包再次带上；一组对重复的报告幂等。同一个包同时带两种报告时，一组先按接任处理，显式切换报告只作审计。
  - 理由：交接核对是否需要，取决于能否证明旧域最后位置与新域起始位置之间无遗漏；这只有连接器掌握。
- **逐项核实帧与错误类型**：大纲 §8.3 列出的 advisory、FutureCursor、终止帧、sync 等，要核实在所选协议版本中的实际名称与语义；有差异时登记，并按变更流程更新映射。
  - 理由：第三方协议会演进，大纲写的是设计时的理解，必须以实际版本为准。

**不要做**

- 不自建 relay / PDS 全量爬取。原因：工程量大、超出 Demo 范围，合规边界也不清晰。
- 不使用未授权镜像。原因见 0.6 节。
- 不采集需要登录才能看到的内容。原因：超出公开数据范围，合规清单无法覆盖。

**测试与验收**

- **M0 软判据**：协议版本与游标解释写入 Manifest 并过夹具；WS 断线重连并按游标续接。须在接入真实来源前销项。
- **M1**：大纲 §8.3 Bluesky 行夹具中归本组的子项（总册附录 C 的 M1-8.1、8.5a、8.6b、8.7、8.8a），其余子项与一组联合。

**必读大纲**：§4.4（连接器 Manifest 补充字段）、§8.3（Bluesky 行全文）、§4.11（缺失观测计数、逐文档核验）、§4.12（删除确认、sync\_unverified 解除条件）、§4.7 第 ⑥ 步（理解账号事件如何被处理）。

## 8. 连接器：news-rss / sitemap

**交付物**

- RSS / Atom 与 sitemap 读取、条件请求、按主机礼貌间隔、来源合规清单（含商业转载条款）。
- **一期接入的源**（项目负责人已拍板：只用免费且无需申请的来源，第 16 节）：政府网站发布的 RSS，例如国家统计局"最新发布"（`https://www.stats.gov.cn/sj/zxfb/rss.xml`）与"数据解读"（`https://www.stats.gov.cn/sj/sjjd/rss.xml`）；其他源须同时满足"robots 不禁止"与"网站声明不禁止本用途"，M0 第 1 周核对后登记到来源配置。要求书面授权才能使用稿件的商业新闻站点（如中国新闻网）一期不接，列为备选（第 16 节）。

**要研究的技术**

- RSS 2.0 / Atom 格式差异（feedparser）、sitemap 协议、HTTP 条件请求（ETag / Last-Modified）、XML 安全解析。

**推荐实现与理由**

- **feedparser 只解析受控传输取得的字节**：SDK 提供一个"只收字节"的包装函数；`connectors/` 禁止直接 import feedparser（import-linter 检查），只能用这个包装函数。
  - 理由：feedparser 收到 URL 时会自己联网，绕过限流、冷却、网络策略与审计。
- **XML 先经 defusedxml 预检**，拒绝 DTD 与实体声明，再交给 feedparser；sitemap 用 `defusedxml.ElementTree` 解析。
  - 理由：外部来源的 XML 不可信，必须先防 XXE 与实体膨胀攻击。
- **使用条件请求**（ETag / Last-Modified）。
  - 理由：内容没变时服务器返回 304，省带宽，也降低被限流的概率。
- **只使用来源许可范围内的字段**（标题、摘要、链接、时间等）；全文抓取须逐站点确认许可。
  - 理由：RSS 只代表"可以发现与订阅"，不代表可以转载全文（大纲 §8.1）。
- **RSS 条目消失、超时、5xx 都不伪造删除**。
  - 理由：RSS 通常只保留最近若干条，条目滚出列表不代表文章被删；误判删除会错误地禁读有效内容（大纲 §4.12）。
- **完整性未知的来源按就绪判定式处理**，不会"一上来就就绪"。

**不要做**

- 不做浏览器自动化或绕过反爬。原因见 0.6 节。
- 不把 URL 交给 feedparser。原因见上。

**必读大纲**：§4.11（FetchPage、违规清单、周期结算）、§8.1、§8.3（新闻 RSS 行）、§4.12（删除确认）。

## 9. 连接器：file 与 http-fixture

**交付物**

## 10. 证据库

**交付物**

- 逻辑证据对象表：EvidenceRef 只绑定不可变出处，URI 为 `evd://sha256:<digest>`。治理属性（分级、保留类别、访问范围）单独版本化，并留变更审计。
- 写入方鉴权：按证据种类限定唯一写入方，凭平台授予的服务身份。
- blob 实例表：（租户，字节摘要，实例 ID），三态 `pending | live | condemned`；同一摘要下至多一个 pending 或 live（部分唯一索引）。
- 上传三步：插 pending 行 → 写字节 → 改 live。
- 引用流水：只增；（持有者类型，持有者 ID，对象，方向）唯一；保留归档基数 + 连续归档前沿。
- 暂存持有与正式持有的完整生命周期；逻辑对象状态机（staged → formal | withdrawn）。
- **证据 API（I6）**：staged 登记（独立事务，先锁任务行；**根来源由证据服务按证据身份与父证据推导**，请求中带的集合只用于核对、不一致即拒绝；锁内复核永久撤回；**实例改绑只在这里进行**）、读取（经 I17 读时可用性判定）、治理属性；**blob 上传三步**（插 pending 行 → 写字节 → 改 live），供提交事务内首次创建种类的写入方在上传准备阶段使用（normalizer 经 SDK、运行时、知识服务），接口 M0 第 2 周冻结。
- **证据库事务内接口（I5）**，事务内适配器，供一组提交段第 ⑧ 步调用：staged 转正、首次创建种类写正式持有、校验 blob live（KEY SHARE）；目标实例 condemned 时让整包返回 `retry_after(blob_condemned)`。
- 回收作业。

**要研究的技术**

- 内容寻址存储与引用计数 GC；PG 大字段存储（bytea + TOAST 与 large object 的取舍）；部分唯一索引。
- Read Committed 下"先取锁、再用独立语句重新汇总已提交流水"的正确写法。
- 生产档对象存储与按实例独立数据密钥：Demo 只保留适配器接口与能力声明。

**推荐实现与理由**

- **按字节摘要去重，但删除作用于逻辑对象**。
  - 理由：两条正文相同的帖子可以共享字节省空间，但删除其中一条不能影响另一条（大纲 §4.3、风险 R30）。
- **引用流水只增**（+1 / −1 记录），不在计数行上原地加减。
  - 理由：热门内容的计数行会成为写热点；只增流水没有热点，也天然留下审计记录。
- **实例行先于字节**：上传第 ① 步先插 pending 行再写字节。
  - 理由：保证不存在"没有实例行的字节"，回收作业才能找到并清理所有字节，包括上传中途崩溃留下的。
- **Demo 字节存 PG 独立表**；第 ② 步在短事务内对实例行取 KEY SHARE，确认仍为 pending 再写。
  - 理由：与回收作业的 `FOR UPDATE` 互斥，迟到的写入不会在回收之后留下可读字节。
- **回收作业**：
  1. 对 blob 行取 `FOR UPDATE`；
  2. 用独立语句重新汇总；
  3. 条件满足才置为 condemned；
  4. 立即提交；
  5. 在事务外异步删字节，按实例 ID 幂等。
  - 理由：在 Read Committed 下，取锁前查到的汇总可能已经过时，必须拿到锁之后重新汇总；删字节放在事务外，避免持锁访问存储。
- **I5 是运行在调用方进程内（编排器提交段）的适配器**：只接收提交上下文（调用方的事务句柄），只在 blob 行 → 逻辑对象行层级取锁，写入前断言根来源已在第 ⑥ 步锁集合内；不开新连接、不提交（总册 §7.4.1）。
  - 理由：这些操作必须和一组的提交在同一个事务里原子完成；另开连接会破坏原子性，还可能等待自己事务持有的锁。
- **改绑不进提交事务**。
  - 理由：大纲 §4.3 规定改绑在暂存登记中进行；提交事务内遇 condemned 只返回 `retry_after(blob_condemned)`，由写入方在事务外重新上传。
- **所有 −1 以 **`ON CONFLICT DO NOTHING`** 写入，并按持有关系键排序**。
  - 理由：唯一约束保证同一持有关系最多减一次；排序避免多条写入之间形成唯一键等待环。

**不要做**

- Demo 不接对象存储。原因见 0.6 节。
- 不按对象计数；不设独立孤儿清理作业。原因见 0.6 节。
- 上传与等待不在持任务行锁的事务内进行。原因：会把网络耗时带进锁持有时间，还可能与回收作业互相等待。
- condemned 不得恢复为 live。原因：condemned 之后字节可能已在删除中，恢复会出现"行说存在、字节已没"的不一致。

**依赖与接口**

- 提供：I5（事务内适配器）、I6（证据 API）。
- 依赖一组：提交上下文接口（`contracts/`）。

**测试与验收**

- **M0 硬判据**：
  - 非授权写入方写来源内容证据被拒（H6）；
  - 两个同正文帖子删其一，另一篇仍可读；回收作业与同正文新帖并发提交，新帖可读；等待回收锁期间提交新引用，回收不删字节（H10）。
- 大纲 §4.3 末尾的 CI 夹具清单全部纳入；I5 的锁序断言用例。

**必读大纲**：§4.3 全文、§4.7（全局加锁顺序、第 ⑧ 步）、§4.12（写屏障）、§9（表结构）。

- **核验与观测登记适配器（I9）**，状态行层级：
  - 存在 / 缺失观测登记，按大纲 §4.11 计数，返回是否达到删除确认与当前 `last_presence_upper_at`；

  - 达到删除确认时，在同一提交事务内写**待确认撤回记录**；记录**一经写入即视为删除确认责任已经确定、不可撤销**（大纲 §4.11"确认后一律按永久撤回处理"）：之后登记的任何 present 都不撤销它，对已有待确认记录的文档不再计数。它**不代表永久写屏障已生效**：写屏障以 I16 提交为生效点，转换前提交的写入照常登记完整根来源、受读时禁用，永久撤回后由扇出处理器清理；转换未完成时不得宣布写屏障到位或清理完成；待确认记录滞留超过阈值时告警，计入删除探测时延；记录记下确认依据（常规缺失确认 / 下界未知按策略计入的"保守来源不可见撤回"），I16 转为永久撤回时一并记入撤回日志与审计；
  - 核验状态只读查询（供一组就绪判定）；
  - 接口签名、字段、错误语义与锁层级 M0 第 2 周冻结；M0 末交付最小真实实现，此前一组提交段不调用它。
- **读时可用性判定（I17）**：所有读取经此判定，依据永久撤回、仍有效的临时原因、逐文档核验条件与待确认撤回记录；覆盖派生对象（结论与指标标"来源核验中"）和检索结果（逐条按核验记录过滤）。一组的 Claim 读取、报告与快照、列表页、就绪判定都调用它。接口 M0 第 2 周冻结；**M0 第 4 周**先覆盖证据读取（含核验记录与来源门控判定，供 H7b、H8 在集成点 2 使用），M1 前半覆盖派生对象与检索。

  - **交接核对的分批承接**（M1，总册 §6.8 第 5 步）：承接只针对按位置域比较的 `account_inactive`；`sync_unverified` 与 `source_gap` 按代次设置和解除，不建交接核对保持。来源处于"交接核对进行中"时，按交接时保存的**账号快照**分批（每批一个独立事务）经 I16 执行"承接本次交接核对责任"的幂等操作：已有未关闭保持的复用原 hold\_id 并记下本次 epoch，没有的新建交接核对保持，已完成本次核对的不重开，已永久撤回的跳过；回访计时器由转换函数为实际新建的保持登记。快照内每个账号都已承接后，经 I16 复核快照并结束本次交接核对；个别保持转人工不阻塞结束；快照之外的新账号不承接；重跑不重复建保持。

  - 删除扇出登记表与删除处理器框架（一组存储的处理器也注册到这里）；
  - 导出登记（I20）：先登记、后交付；区分受控 / 非受控副本，记录撤回能力，对非受控副本分别记录"已通知 / 已确认 / 不可验证"。
- **本组存储的删除处理器**：证据层（撤回逻辑对象、写 −1、交给回收作业）、向量 / 全文 / 指纹索引、话题成员与话题中心缓存、指标结果、知识事实、网关精确缓存与反向索引、应用侧检索缓存、进程缓存。
- **清理完成判定**：全部处理器完成、相关进程连续前沿到位、引用不可读、删除后写入被拒等（大纲 §4.12）。
- **缺失观测计数**：多资源 missing 与单资源 gone 同一规则；新鲜性下界已知、陈旧观测、present 只经抬高上界打断、下界未知按来源策略并审计区分。
- **resync 清扫**（M2）：清扫集合、AppView 批量回访、预授权自动恢复。

**要研究的技术**

- 扇出式清理与完成判定。
- 时间区间推理：新鲜性上下界，以及为什么两个下界相比不能证明先后。
- 排序域与位点映射（无缝切换的重叠 / 无缺口 / 衔接覆盖验证）。

**推荐实现与理由**

- **每个存储门面在注册时声明删除处理器**；CI 检查扇出登记表与门面写入 API 一一对应。
  - 理由：删除最容易漏的是"后来新加的存储"；把登记做成注册的一部分，并由 CI 检查，新存储不登记就过不了 CI。
- **"禁读"与"清理"分开**：获知删除即禁读，清理在后台按扇出进行。缺失计数达到确认时，待确认撤回记录与观测登记同一事务写入，从这一刻起禁读，不等处理器调用 I16。
  - 理由：清理可能很慢（缓存、索引、外部副本），但合规要求是"获知即不可读"（大纲 §4.12）。
- **平台派生的控制变更一律经 I16**，本组不直接改控制行状态。
  - 理由：控制状态只能由一组的同一个转换函数改变，避免出现第二套状态更新协议；连接器的删除标记仍只经 `tombstones[]`，缺失计数确认是平台派生的确认（大纲 §4.12"独立删除事务"）。
- **核验与计数逻辑写成"纯函数 + 薄事务外壳"**。
  - 理由：规则涉及大量时间区间比较，写成纯函数后可以对乱序、重复、陈旧观测做排列测试，比集成测试快得多、覆盖更全。
- **缺失观测按"存在证据上界 vs 缺失下界"比较**。
  - 理由：只有缺失的最早可能时刻晚于存在的最晚可能时刻，才能证明"先存在、后缺失"；用两个下界比较证明不了先后，会把缓存过期造成的假缺失误判成删除。
- **I7、I9 是运行在调用方进程内的适配器**（编排器提交段，或调用 I16 的本组平台服务），遵守总册 §7.4.1 的锁约定。

**不要做**

- 不以首次抓取、入库、发布时间或 observation\_epoch 替代核验。原因：这些时间只说明平台什么时候看到，不说明看到的数据有多新；断流期间被删的帖子可能以陈旧缓存的形式被"首次看到"（风险 R40）。
- 不让 present 无条件打断缺失计数。原因：迟到的陈旧缓存会无限推迟真实删除的确认（大纲 §4.11）。
- 非受控副本不冒充"已删除"。原因：用户下载到本地的文件平台无法验证删除，只能如实记录。
- 清除范围级原因不放行未核验文档。原因：范围级原因只表示"清扫进行中"，文档是否可读要看逐文档核验（大纲 §4.12）。
- 不绕过 I16 直接更新控制行。原因见上。

**依赖与接口**

- 提供：I7、I8 接收端、I9、I17、I20。
- 依赖一组：控制状态转换与撤回日志发布（I8）、平台控制变更入口（I16）、控制对象行字段语义。

**测试与验收**

## 12. 模型网关

**交付物**

- 统一模型接口：生成与嵌入；容量配额；精确请求结果缓存（结论、定级、指标禁止近似复用）。
- schema 强制；只重试传输类错误；工具白名单；secrets 管理；多供应商适配。
- **服务端写证据**：调用返回时登记 model\_output（staged，发起任务持有）。
- **反向索引**：提示词中的来源内容只能经 SDK 从证据引用填入，网关据此登记，原文删除时可遮蔽相关模型输出。
- **精确缓存与删除处理器**：缓存条目按反向索引登记来源；原文删除时删除相关缓存条目。

**要研究的技术**

- 主流 LLM API 形态（如 OpenAI 兼容接口）、结构化输出（JSON Schema 约束、校验失败重试）、嵌入接口。
- 请求规范化与摘要作缓存键；零留存与私有化部署选项。

**推荐实现与理由**

- **网关作为独立服务**。
  - 理由：模型密钥、配额、缓存都集中在一处；换模型、换供应商只改网关配置，Agent 代码不动。
- **提示词只接受"模板 + 证据引用"**，网关从证据库取原文填入并登记反向索引。
  - 理由：网关因此知道每次调用用了哪些原文；原文被删时，能找到并遮蔽由它生成的模型输出（大纲 §4.12）。
- **模型输出由网关服务端直接写入证据库**。
  - 理由：Agent 无法篡改模型输出后再冒充原样提交，证据才可信（风险 R26）。
- **精确缓存键包含全部影响输出的因素**：租户与执行命名空间、模型与版本、全部调用参数、模板与配置版本、结构化输出与工具定义、按顺序排列的输入证据身份及其内容版本摘要。
  - 理由：少一项就可能跨租户、跨模板或跨证据版本误命中；只缓存精确命中，结论与输入严格对应。
- **命中缓存后**：
  - 重新检查当前任务的权限、撤回状态与读时门控；
  - 经网关证据写入路径为**当前任务**登记暂存持有（按 staged 登记的锁序，锁内复核永久撤回）；
  - 保留原调用的出处记录；
  - **不得返回当前任务没有持有的旧 EvidenceRef**。
  - 理由：缓存命中不能成为绕过撤回屏障与引用记账的后门。
- **缓存填充的屏障覆盖到最终写入**：网关精确缓存是平台服务内的持久缓存，写入按总册 §7.4.1 第 5 款的锁序进行并在锁内复核永久撤回，不只在取数阶段检查。
- **只重试传输类错误**。
  - 理由：模型输出不合格属于内容问题，盲目重试会放大成本并掩盖提示词缺陷，应由 schema 校验与上层逻辑处理。
- **模型服务方**：零留存**不等于不发送**——内容仍会发给服务方，只是服务方承诺不保存。大纲 §15 第 2 项**已拍板**（总册 §7.3 决策点 2），网关按下面两套后端配置实现，切换只改网关的供应商配置：
  - **方案一：DeepSeek API（Demo 阶段，现行）**。生成类调用走 DeepSeek 的 OpenAI 兼容接口；具体模型名与版本以开通时的官方文档为准（2026-10 官方价格页列出 `deepseek-flash` 与 `deepseek-v4-pro` 两个模型，均为 1M 上下文）。按其公开隐私政策，请求在中国境内存储、可能用于模型训练、没有零留存选项，属于"经合规确认后使用其他服务"：合规确认之后才启用，合规清单写明"发给 DeepSeek 的来源内容平台撤回不到"。
  - **方案二：平台内部署 Qwen（服务器到位后）**。用 vLLM 部署 Qwen 开源模型，约 35B 级，例如 Qwen3.5-35B-A3B（总参数 35B、每次激活约 3B 的混合专家模型，Apache-2.0 许可，原生 262K 上下文，支持工具调用），经网关以 OpenAI 兼容接口接入；来源内容此后不再出平台。硬件参考：INT4 量化单卡 24GB 起，32GB 更从容；FP8 需一张 80GB 级显卡（如 H100）；BF16 需两张 80GB 卡或一张 H200。服务器选型由项目负责人落实，不占两组人周。
  - **嵌入后端（两套方案共用）**：DeepSeek API 不提供嵌入模型，所以在网关后挂一个**平台内运行的开源中文嵌入模型**，例如 Qwen3-Embedding-0.6B（Apache-2.0，最大 1024 维，可用 CPU 运行），供必做的 embedder 使用。它只是网关的一个后端，不属于 Phase 2-A 的"模型私有化与路由"能力。约 0.3 人周（总册 §7.3 决策点 2 已触发）。切换生成类后端时嵌入后端不变，向量不需要重算。
  - **切换的约束**：模型与版本进入执行配置锁与精确缓存键，切换后不会命中旧缓存；结构化输出与工具调用在两套后端上都要过同一套 schema 校验夹具；切换后按新组合重跑组合评估（总册 §7.3），DeepSeek 上的组合评估记录不沿用；网关配置变更按总册第 11.1 节二级变更登记。
  - 接入新的模型服务属于本节"多供应商适配"，在 M1 网关 0.8 之内；模型资源本身由项目负责人落实。
  - 理由：服务方一旦留存请求，已删除的来源内容就留在了平台之外，平台撤回不到；embedder 是必做，topic-assigner、clusterer 依赖它的向量，没有平台内嵌入模型，M1"首次经网关的端到端"会在嵌入这一步断掉。

**不要做**

- 不做语义或近似缓存。原因见 0.6 节。
- 不允许 Agent 绕过网关直连模型。原因见 0.6 节。
- 被观测的 AI 产品不得充当推理后端。原因：被观测对象和观测工具混用，会污染观测结果，也违反底线 2。
- 缓存命中不直接返回旧证据引用。原因见上。

**依赖与接口**

- 提供：I11。依赖本组证据库（I6 路径）与读时可用性判定（I17）。

**测试与验收**

- M1：真实链路首次经网关（生成类走 DeepSeek API，嵌入走平台内嵌入后端）；两套生成类后端的配置切换夹具（同一请求在两套配置下缓存互不命中、结构化输出校验一致）；模型输出与原文字节相同时，原文删除后模型输出经反向索引遮蔽；不同租户 / 不同模板版本的相同提示词不互相命中；命中后当前任务持有新登记、已撤回证据的命中被拒。

**必读大纲**：§2.2（底线 2）、§3.3（Model Gateway）、§4.3（写入方表）、§4.12（模型输出与缓存、模型服务方）、§15（第 2 项）。

## 13. 知识服务与指标目录

**交付物**

- **四类知识的存储与查询 API**：
  - 规范型（法规与沿革）；
  - 经验型（案例）；
  - 事实型（文档、传播边、观测账号、互动序列 + 指标）；
  - 主数据型（实体与别名、辖区树、事权对照、账号标注、平台渠道目录、采集查询内容）。
- **指标目录**：参数化 `metric_id`、不可变 `metric_result_id`、版本化只读视图。
- **知识快照**：（数据 as\_of 水位，目录 / 索引版本）。
- **派生写入门面（I10）**：事务内适配器，供一组提交段第 ⑩ 步写入向量、全文、指纹、话题成员；状态行层级，写入前断言根来源已锁。**M0 第 4 周交付最小真实实现**（一种派生种类 + 屏障，不晚于集成点 2 的删除屏障夹具开始，参与 H7b、H9），M1 补齐其余种类。
- **检索**：pgvector 精确检索 + jieba / BM25，按读时可用性判定与核验记录过滤门控来源。
- **应用侧 BM25 缓存的删除处理**：见下。

**要研究的技术**

- pgvector：精确距离查询、维度与 embedding 版本管理。
- 中文检索：jieba 分词、BM25。
- valid-time 时态建模；参数化 SQL 视图；去重与四种统计口径。

**推荐实现与理由**

- **四类知识分开存储与查询**。
  - 理由：法规按条文与沿革查，案例按相似度查，事实按身份与图遍历查，主数据按键查；查法完全不同，统称"RAG"会让每一类都查不好（大纲 §1、§7）。
- **向量不建 ANN 索引，用精确检索**。
  - 理由见 0.4 节；规模上来后在 Phase 2 再评估 HNSW。
- **应用侧 BM25 是"内容派生的进程缓存"**：
  - 声明为可重建，登记反向索引、缓存位置与撤回处理器，并按第 5 节回报撤回前沿；最终发布与撤回应用经同一缓存临界区（第 5 节）；
  - **只放在进程内存中，不落缓存目录**；持有它的知识服务进程与 worker 一样经 `register_process` 注册、回报前沿；所在容器配一个监督器，进程退出后提交 `report_retired`，依据是"进程已终止，内存缓存随之消失"（备选：为该缓存声明最长存活期，到期强制重建，大纲 §4.12 允许以"缓存最长存活期已过"作为完成条件）；
  - **按执行上下文锁定的知识快照构建**：缓存键包含命名空间、数据水位与目录 / 索引版本；候选内容先满足该快照的选择条件，再经读时可用性判定与撤回检查（删除优先于快照）；
  - 禁止从历史缓存或快照恢复已经撤回的内容；不禁止查询仍然可用的历史版本；同时可能存在多个快照的缓存实例，沿用现有缓存资源上限；
  - rank\_bm25 不支持增量删除，删除时整体重建，Demo 数据量下可以接受；
  - 若要持久化，必须经派生写入门面写入 PG 倒排表，并登记删除处理器。
  - 理由：BM25 索引里含有来源文本的分词结果，属于删除扇出范围；不登记就会成为删除的漏网之处。
- **指标结果按（metric\_id，参数，数据水位）计算后不可变落表**，报告槽位引用结果身份。
  - 理由：报告引用的数字永远能找到当时的计算结果，不会因为数据更新而"悄悄变了"。
- **事实表只增 + valid-time；向量索引按不可变版本 + embedding 版本管理**。
  - 理由：知识快照才能复现某个时点的状态；embedding 模型更换时，新旧向量不会混用（风险 R11）。

**不要做**

- 不引入 Elasticsearch / OpenSearch / 图数据库。原因见 0.6 节。
- 结论类不做近似缓存。原因见 0.6 节。
- 快照不能复原已删内容。原因：当前删除优先于历史版本锁，否则快照就成了绕过删除义务的后门（大纲 §4.10）。
- Agent 与服务不直连 PG 读写知识表。原因：底线 3，状态与派生写入都经平台门面。

**依赖与接口**

- 提供：I10、I12。

**测试与验收**

- M0：I10 最小真实实现参与 H7b、H9。
- M1：知识服务与指标目录可被 Agent 与报告槽位使用；门控来源的检索结果被过滤；删除一条源帖后 BM25 缓存重建且不再命中；锁定 T1 快照的查询不混入 T2 之后的数据，而 T1 中后来被删的内容仍不可读；在"复核后、发布前"注入撤回，没有缓存条目在前沿推进后复活。

**必读大纲**：§2.2（底线 3）、§3.3、§4.3、§4.6、§4.7（第 ⑩ 步、全局加锁顺序）、§4.10、§4.12（门控覆盖派生对象）、§7（四类知识、指标目录、去重与口径）。

  - 存储不变：普通个人的作者标识始终按大纲可逆假名化存储，演示模式只作用于展示与导出；
  - **假名反查服务**：内部模式下把假名还原为真实作者标识供页面与报告显示；只接受平台服务身份调用（控制台后端、报告渲染），映射表单独授权；外部模式下拒绝调用；
  - **外部模式遮蔽库**：不反查；正文、引文与证据钻取中的 @账号、个人主页与原帖链接、entity-resolver 识别出的普通个人姓名，按同一假名映射一致替换（同一人在全部页面和报告里是同一个假名）；官方 / 认证账号（账号标注表）不替换；证据原文下载关闭；
  - 模式是部署级开关（启动参数或控制台管理开关，开关由一组实现），切换写审计；页面与导出带模式标记。

- 标注支持：与标注人员和一组 golden set 配合；标注批次登记到导出登记表；真实增量数据接入准备。

**推荐实现与理由**

- **作者标识用按"租户 + 来源"加密的键控哈希**。
  - 理由：原生 ID 里含个人标识，库内只存哈希；用键控哈希而不是普通哈希，防止有人用公开 ID 反推（大纲 §4.3）。
- **遮蔽在展示层做，不改存储**。
  - 理由：同一份数据要能在内部、外部两种演示之间切换；存储始终按大纲假名化，切换不需要重算或复制数据，也不会因为切换而留下真实标识的副本。
- **标注优先在系统内完成**，导出的标注批次登记。
  - 理由：真实采集样本同样受删除约束，系统外的副本难以撤回（大纲 §4.12）。

**不要做**

- 合成语料不用于报准确率。原因：合成数据的分布和真实舆情不同，准确率没有参考价值（大纲 §11）。
- 外部模式不调用假名反查服务，也不在导出里附带映射表。原因：对外演示时任何真实标识都不能出现在页面或导出物里。

**测试与验收**

- M1：外部模式下页面、报告、导出与证据钻取中不出现普通个人的真实标识（作者、@账号、个人主页 / 原帖链接、识别出的姓名），同一人假名一致；官方 / 认证账号不被替换；外部模式下反查服务拒绝调用；模式切换写审计；内部模式能显示真实作者标识。

**必读大纲**：§4.3（作者标识）、§4.6、§4.10、§4.12（评测与标注的删除约束）、§7（评测体系）、§11（验收口径）、§15（语料来源）。

- 评测记录标明所用的模型资源；全规则基线或模拟输出的端到端评测只能作基线，不能当作大纲"范围界定"要求的"模型 + 提示词 + 检索 + 规则"组合评估（总册 §7.3 决策点 2）。组合评估的验收归属见总册 §7.3：M2 出口第 5 条须有含大模型的组合运行记录，到 M2 出口仍缺时不得标为已验收，按总册 §10.2 第 3 款升级（总册附录 C 的 M2-5.1）。

**为什么需要**

- 逐条评测只能回答"报出来的对不对"，回答不了"该报的有没有报"。舆情监测最怕漏报，所以要用应报事件清单单独评召回与时延（大纲 §7）。

**测试与验收**

- M2：应报事件清单的召回与时延有评测记录，记录注明所用模型资源，组合运行记录按 M2-5.1 判定。

- **可观测栈**：OTel（关闭载荷采集）+ Jaeger + Prometheus。两组各自为模块埋点；span 属性与标签不得含原文，日志不记原文。

**推荐实现与理由**

- **页面只经只读接口读数据**，不直接读一组内部表。
  - 理由：一组内部表结构调整时页面不用跟着改；隔离与门控在接口层统一执行。
- **关闭 OTel 载荷采集，span 与日志不含原文**。
  - 理由：追踪与日志系统往往没有删除扇出；原文一旦写进去，删除义务就无法履行（大纲 §4.12）。
