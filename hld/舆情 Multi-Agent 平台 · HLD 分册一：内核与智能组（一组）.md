## 怎么用这份文档

- **开发以本分册为主**。每个模块按七项组织：交付物、要研究的技术、推荐实现（含为什么这样选）、不要做（含原因）、依赖与接口、测试与验收、必读大纲章节。
- **"必读大纲"是规则规范**。锁模式、状态转换条件、判定规则、CI 夹具以大纲为准，实现必须逐条满足。本分册不复制这些规则，只告诉你去哪一节看、怎么落地。
  - 每个模块的必读范围 = 总册 §0.2 的**公共必读**（大纲 §2.1–2.4、§4.6、§4.9）∪ 该模块列出的章节。
  - 列表不是豁免：实现中碰到列表以外的规则，照样要读并满足；发现漏项按总册 §11.4 登记。
  - 模块主责维护本模块的"规则—实现—夹具"对照表（总册 §0.2）。
- **"推荐实现"是起点，不是定论**。每条推荐都写了理由。改动按总册 §11.1 定级：
  - 在推荐实现范围内调整细节、在本分册列出的验证候选之间做选择：一级，组内代码评审；
  - 替换推荐方案或引入新的第三方组件，**即使不改跨组接口**：至少二级；
  - 涉及跨组接口或锁约定：三级；触及大纲冻结范围：四级。
- **"不要做"是边界**。每条都写了原因和什么情况下会重新考虑。确有必要时同样走变更流程，不要先做再说。
- **有疑问第一时间提**。对推荐或不采用的技术、对理由本身有任何疑问或不同意见，按总册 §11.4 登记，不要带着疑问开发。

## 0. 本组概览

### 0.1 职责

定义并执行"结果怎么校验、怎么提交、怎么用"：

- 运行时核心（含控制状态转换、平台控制变更入口、撤回日志与发布、状态服务）；

- 本组存储的删除处理器；
- 报告、校验库（骨架自二组转交）、校验规则与评测；
- 控制台列表页与只读接口、目标环境回归。

### 0.4 本组技术栈与选型理由

"大纲指定"表示该选择已写入大纲 §10 或相关章节，改动需走变更流程；"建议"表示本 HLD 的推荐，可在 M0 第 1 周技术验证后按一级（候选之间选择）或二级（候选之外）调整。

| ------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 语言     | Python 3.11+（建议版本）                                                               | 大纲的 SDK 与 worker 模型（asyncio、spawn、BLAS 线程、import-linter）按 Python 设计；NLP、聚类、统计生态完整；两组同一语言，契约模型只维护一份。3.11 起有 asyncio TaskGroup 且性能明显提升       | Go / Java：运行时更快，但 Agent 与算法生态在 Python，会变成两种语言、契约维护两份；Demo 的瓶颈在 PG 与模型调用，不在语言                                                                                                             |

### 0.5 M0 第 1 周技术验证（先验证再开工）

1. **PG 锁冲突与锁序守卫原型**：在两条连接上验证四种行锁模式的冲突关系、`SKIP LOCKED` 行为、死锁错误码 40P01 的捕获与重试；同时做出 failpoint 屏障测试框架。
   - 原因：提交段和 M0 硬判据都建立在这些行为上，先用实验确认，避免整套实现建在错误理解上。
2. **Kafka 幂等生产者**：验证 `enable.idempotence=true, acks=all, retries>0, max.in.flight≤5` 下的回调顺序与重试语义。
   - 原因：外发箱的确认逻辑依赖这些语义。
3. **RFC 8785 实现选型**：评估现成库，或者自实现并通过 RFC 测试向量。与二组共同决定。
4. **CEL 库选型**：确认所需表达式子集可用；能限制表达式长度、输入集合大小与可用函数；能控制求值成本或设超时；能禁用非确定性函数与任意扩展。
5. **契约工具链**：Pydantic v2 → JSON Schema 导出、字段元数据（digest include / exclude）方案；"线解码模型保留未知枚举值"的写法（第 1 节）。
6. **Worker 协议传输形态**：HTTP/JSON 还是 gRPC。第 2 周冻结前定稿。
7. **决策表穷举规模与耗时**：按冻结的维度算出组合总数，测单机穷举耗时，据此确定 CI 分片与夜间全量方案。

### 0.6 本组不采用的技术与原因

| 不采用                                          | 原因                                                                                                                                   | 什么情况下会重新考虑                      |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------- |
| Celery / RQ / Dramatiq 等任务队列                 | 它们默认的执行、确认与重投语义承载不了任务表、键占用与原子提交：任务状态不能和业务写入在同一个 PG 事务里提交，也就做不到大纲要求的租约 fencing、键占用顺序和"恰好生效一次"。Celery 虽然有 PG 结果后端，但那只保存执行结果，不参与我们的提交事务 | 不会；任务表是设计核心                     |
| Temporal / Airflow / Prefect 等编排框架           | Temporal 可以用 PG 做持久化，但它的工作流历史与我们的业务写入不在同一个事务里，做不到"状态转换与结果写入原子提交"，还需要独立集群；大纲已标为"待独立决策、未排期"。Airflow / Prefect 面向批调度，不适合事件驱动的低延迟处理      | 产品化阶段出现长流程编排需求时，单独立项评估 Temporal |
| Kafka 事务 / exactly-once 作为正确性依据              | exactly-once 只覆盖 Kafka 内部的"读—处理—写"，管不到 PG 写入。大纲以 PG 事件表为权威，Kafka 只做传输，下游按事件身份去重                                                      | 不会                              |
| Debezium 等 CDC 工具替代转发器                       | 需要额外部署 Kafka Connect；也难以实现大纲要求的按键确认、毒行隔离与暂停该键                                                                                        | 外发量很大、需要同步到多个目标系统时              |
| protobuf / Avro + Schema Registry            | 线格式已定为 CloudEvents JSON；二进制格式加 schema registry 多一套组件，Demo 体量不需要                                                                      | 跨语言服务大量增加、带宽成为瓶颈时               |
| 用 ORM 会话管理提交路径事务                             | 提交路径要逐条审查加锁语句与顺序；隐式 flush 与懒加载即使能关，也要逐处确认，统一用显式 SQL 审查成本最低                                                                           | 不会用于提交路径；只读查询与后台工具可以用           |
| 提高隔离级别（REPEATABLE READ / SERIALIZABLE）代替锁序设计 | 序列化失败需要整事务重试，同一控制对象、同一作业行这类高冲突路径会反复失败；大纲的正确性论证建立在 Read Committed + 显式行锁之上                                                            | 不会                              |
| LangChain / LlamaIndex 等 Agent 框架作为运行时       | 它们自带网络调用、工具调用和记忆，会绕过模型网关、网络策略和证据登记，违反底线 2、3                                                                                          | 可以借鉴提示词与输出解析写法，不引入运行时           |
| 让模型定风险等级、在报告里自己写数字                           | 不可复现、不可审计；原投标方案"规则与模型同时定级、权威不明"正是这次要改掉的问题                                                                                            | 不会                              |
| 结论类的语义缓存 / 近似复用                              | 结论、定级、指标近似复用会让输出与输入不符，大纲 §3.3 明确禁止                                                                                                   | 不会用于结论类                         |
| 模型训练、微调                                      | 不在本项目范围（大纲范围界定）                                                                                                                      | 后续单独立项                          |

## 1. 契约定稿（`contracts/`）

**交付物**

- 事件信封（CloudEvents 1.0 线格式与扩展属性）、Claim、Manifest（全字段与缺省展开规则）、执行上下文与模式权限表、WorkflowSpec / Run / Task。
- Worker 协议消息、结果包与 `semantic_bundle_digest` 逐字段标注、提交结局枚举（含 `retry_after` 的 `pg_admission` 与 `blob_condemned` 两种原因）、分段收口规则；签名材料中的根来源集合。
- FetchPage 与 item\_outcomes、决策表（18 行判定规则）与违规清单（19 条）YAML、状态与错误枚举、ID 派生输入规范。
- **事务内接口与锁约定**（总册 §7.4.1）：提交上下文接口（事务句柄、已锁根来源集合、锁层级守卫）、各适配器所属锁层级。二组的事务内适配器只依赖这个接口。
- **控制对象行字段语义与列清单**（与总册 §3 同一清单）：撤回代次、availability 与各原因位置；每次并入的冲突类型与时刻（判定保持有效性用）、比较键、handoff\_epoch（两端位置；接任时旧域位置可为"未知"）与"交接核对进行中"标记（含 handoff 建立时刻）、当前权威位置域及建立它的作业与指定版本、接任空档记录（按 `source_gap` 代次保存两端位置——左端可为"未知"——、建立依据与登记时刻，可多条，单独建表）、交接账号快照（单独建表，由 I7 生成并逐账号记"已承接"）、保持上记下的 handoff\_epoch、覆盖前沿、覆盖证明参照时刻。二组据此写 DDL、迁移与索引。
- **ValidationRecord** 六维结构与存储表（校验库骨架复用）。
- 报告契约、谓词注册表结构、领域包三类内容的 schema（M0）。
- 证据与标准文档部分和二组共同定稿。
- 契约兼容性测试骨架。

**要研究的技术**

- CloudEvents 1.0 规范：必选属性；扩展属性命名只允许小写字母数字。
- JSON Schema 2020-12 与 Pydantic v2 模型导出。
- RFC 8785 JSON 规范化；语义化版本与契约演进（只增可选字段、禁止静默改义）。

**推荐实现与理由**

- **Pydantic v2 模型是契约的唯一来源**，导出的 JSON Schema 落盘到 `contracts/schemas/`，CI 比对导出结果与提交版本。
  - 理由：代码和 schema 只有一个来源，CI 能自动发现静默改义（大纲 §4.9 禁止）。
- **字段元数据集中声明**：`digest: include | exclude`、缺省语义、是否可路由。SDK（二组）读取这份元数据计算摘要。
  - 理由：如果两组各写一份字段清单，迟早不一致，回执幂等就会出错。
- **FetchPage 分两层模型**：
  - 线解码模型：检查结构、必填字段与基本类型，**枚举类字段以字符串接收、保留未知值**，不静默丢字段、不做会改变摘要的类型转换；
  - 判定输入：未知值交给违规清单判定（V1–V19 分类），而不是在解码阶段直接报错；
  - 构造与输出模型（SDK 组装、运行时内部使用）可以用严格枚举。
  - 理由：如果请求模型用严格枚举，未知 status 会在解码阶段被框架直接拒绝，绕过违规分类与受限投影，墓碑也随之丢失。
- **决策表与违规清单写成版本化 YAML，配一个纯函数判定器**：输入 FetchPage + 调度上下文，输出 verdict、violation\_codes、primary\_violation、匹配的动作行。运行时与 CI 全组合穷举共用这一个判定器。
  - 理由：YAML 版本可以写进执行配置锁与 PageResult（大纲 §4.11）；纯函数没有数据库依赖，才能跑全组合穷举。
- **事件信封显式映射**，配序列化一致性测试。cloudevents SDK 只用作对照校验。
  - 理由：大纲 §4.1 对扩展属性有自己的约束（如 `causedby` 上限、`subjectseq` 字符串编码），不能依赖 SDK 的默认行为。

**不要做**

- 不引入 protobuf / Avro + schema registry。原因见 0.6 节。
- 不用 ORM 模型充当契约。原因：ORM 模型跟着表结构走，而契约要跨进程、跨版本保持稳定，两者变化节奏不同。
- 不允许 Agent 或连接器自定义字段语义。原因：字段语义一旦分叉，历史数据就无法解释，这属于大纲 §2.1 禁止的 C 类裁剪。

**依赖与接口**

- 与二组联合冻结第 1 批：M0 第 1 周，执行上下文、受控传输接口、FetchPage、状态与错误映射、ID 派生。
- 第 2 批由本组主导：M0 第 2 周，提交协议、事务内接口与锁约定、控制协议、控制对象行字段语义、状态服务。
- 两批都需双方接口负责人签字。

**测试与验收**

- 契约一致性测试，覆盖信封、Claim、标准文档、采集作业、决策表完备性。
- FetchPage 解码夹具：未知 status 但墓碑有效的包进入违规分类且墓碑经受限投影登记；结构损坏的包在解码层拒绝。
- 两批冻结按期完成。

**必读大纲**：§2.1–2.3、§4.1–4.6、§4.7（Worker 协议、全局加锁顺序、第 ⑥ 步、ID 派生、digest、提交结局、分段收口）、§4.8、§4.9、§4.11（FetchPage、决策表、违规清单、完备性测试）、§4.12（控制对象）、§7（领域包）、§9（控制对象行字段）。

## 2. 事件物化、任务与键占用

**交付物**

- PG 事件表（唯一权威日志）与入口物化器：每分区串行，消费位点与物化同一事务，带分区所有权代次。
- 任务表与状态机（8 种状态）、租约（lease\_token + 租约代次 + 到期时间）、键占用表与 `enqueue_seq`。
- causal 序列域前沿维护与缺口补齐；回放从 PG 事件表生成任务。
- **任务创建 API（I2）**：所有新建任务路径的唯一入口，包括提交段续采、定时服务（含保持回访计时器）、显式恢复。它在作业行 `FOR NO KEY UPDATE` 锁内复核代次、栅栏与作业状态，并持锁至提交。

**要研究的技术**

- PostgreSQL 四种行锁模式的冲突关系：
  - `FOR KEY SHARE` 只与 `FOR UPDATE` 冲突；
  - `FOR NO KEY UPDATE` 与 `FOR SHARE`、`FOR NO KEY UPDATE`、`FOR UPDATE` 冲突。
- `SELECT … FOR UPDATE SKIP LOCKED` 的任务领取模式；Read Committed 下的可见性与重读。
- Kafka 消费者分区分配与手动位点管理（位点存 PG，不依赖 Kafka 位点提交）。
- 每键串行的有序消费模型。

**推荐实现与理由**

- **Kafka 只做传输**。消费到的消息在一个 PG 事务内写事件表、派生任务、更新位点，提交后才算消费；Kafka 位点提交只是加速。
  - 理由：物化与位点同事务，崩溃后不会出现"位点前进了但事件没落库"或反过来的情况（大纲 §3.2）。
- **领取用 **`SKIP LOCKED`** 选候选**；有序消费者再检查键占用，只领该键最小 `enqueue_seq` 且无在途的任务。重试中的最小任务即使未到 `retry_at`，也阻塞同键后项。
  - 理由：`SKIP LOCKED` 让多个领取者互不阻塞；键占用保证同键顺序（大纲 §6.1）。
- **causal 缺口处理**：序列域前沿在订阅过滤之前维护并落 PG。
  - 小于已应用值且身份一致的按重复丢弃，身份不一致报冲突；
  - 大于期望下一号时，从事件表按序号补齐；补不到则暂停该键并告警。
- **任务创建 API 遵守大纲的新建锁序**：计时器与显式恢复按"新建任务行 → 作业行"；提交段的续采在第 ⑫ 步已持作业行锁时创建。不用 `FOR SHARE`。
  - 理由：避免创建事务随后更新作业行时锁升级（大纲 §4.11）。
- **编排器进程不持有权威状态**，两个实例同时运行（底线 7）。
  - 理由：任何实例崩溃都不丢状态，可以随时重启或扩容。

**不要做**

- 不以 Kafka 事务或 exactly-once 作为正确性依据。原因见 0.6 节。
- 不用 Celery / RQ / Temporal 等现成框架替代任务表。原因见 0.6 节。
- 不在进程内存保存权威状态。原因：违反底线 7，单实例崩溃即丢数据。

**依赖与接口**

- 依赖二组：PG 连接池与 Kafka 客户端适配器、定时服务（调用任务创建 API）。

**测试与验收**（M0 硬判据）

- causal 缺口从日志补齐；已入队任务领取顺序；单任务模式下前项整包失败阻塞后项；崩溃后唯一有效结果；双实例集成测试。

**必读大纲**：§3.2（集中分发）、§3.3（PG 事件表）、§4.7（全局加锁顺序）、§4.11（代次变更协议中"新建任务的事务在作业行锁内复核"一段）、§6.1–6.3。

## 3. Worker 协议服务端、计算段与状态服务

**交付物**

- `lease / heartbeat / checkpoint / complete / fail` 服务端（I1）。Demo 的 `checkpoint` 返回 `unsupported`，计划解析拒绝依赖它的任务。
- 计算段校验器，在事务外运行，确定性校验以下各项：
  - 结构、范围、枚举；
  - 引用检查（证据存在、哈希一致、quote 匹配、证据种类与生产者、血缘闭包、extraction 的 span 属于 `subject.doc`）；
  - 槽位外文本扫描、query digest 重放。
- **根来源集合汇总**：对本包全部写入（Claim 引用的证据、状态写入、`derived_writes[]`、staged 转正、提交事务内首次创建的对象）求根来源文档与作者账号的并集，写入签名材料，供第 ⑥ 步加锁（总册 §7.4.1）。
- 签名材料：HMAC，绑定 `semantic_bundle_digest`、操作类型、任务、segment、租约代次、配置锁、策略版本、输入快照、`pre_control_epochs`、根来源集合；区分控制变更前提与变更后写入投影。
- `fail` 三结局；PG 准入（满载时返回 `retry_after(pg_admission)`）。
- **状态服务（I19）**：Agent 状态的读取、期望版本校验、模式范围与错误枚举；写入在提交段第 ⑨ 步。二组 SDK 状态 API 是客户端。

**要研究的技术**

- HMAC 与密钥管理（Demo 用本地密钥文件，不下发给 worker）。
- 递归 CTE 查询血缘闭包；Unicode 码点偏移下的 quote 定位（依赖 cleaner 的区间映射）。
- HTTP/JSON 与 gRPC 两种服务形态的取舍。

**推荐实现与理由**

- **协议走网络 API，推荐 HTTP/JSON**，第 2 周冻结前定稿。
  - 理由：worker 不持有数据库凭据（底线 3），只能经网络调用运行时。HTTP/JSON 与 CloudEvents JSON 线格式一致，可以直接复用 Pydantic 模型，抓包和调试都方便。gRPC 性能更好，但 Demo 的瓶颈在 PG 提交，不在 RPC 开销。
- **计算段只读**，不调用远端模型或外部 API，不做无界重算；提交段只验签和做锁内复核，不重算。
  - 理由：大纲要求网络等待不持有数据库连接；把重计算放在事务外，提交事务才能短、锁持有时间才可控。
- **上传准备阶段在计算段之前**：本包提交事务内首次创建的统计结果、规则决策，由其写入方（运行时 / 知识服务）在事务外先完成上传三步，然后才进入只读的计算段与签名；遇 `retry_after(blob_condemned)` 重提时同样先做这一步（来源正文由 normalizer 经 SDK 上传）。上传经证据 API（I6）的 blob 上传接口完成。上传期间不持任务行或控制对象行锁；实例变化不改变逻辑身份、内容摘要与结果包语义摘要。
  - 理由：首次创建种类的字节必须在提交前写好，而计算段要保持只读、可复现；把上传单列为一个阶段，两组对"计算段做什么"的理解才一致。
- **剔除规则，按包类型区分**：
  - **非采集包**：所有根来源处于永久撤回状态的条目及其依赖写入，确定性剔除并记录；全部输出被剔除时，任务以 `skipped_withdrawn` 结束。
  - **采集包**：即使内容条目全部被剔除或本来为空，**仍按正常路径处理**控制信号（`tombstones[]`、账号控制信号）、PageResult、覆盖声明、检查点推进与作业结算，**不以 **`skipped_withdrawn`** 结束**。被剔除的只是内容条目。
  - **待执行阶段的采集任务**（例如目标文档已永久撤回的回访任务）：仍按大纲 §4.12 以 `skipped_withdrawn` 结束，并按大纲 §4.11 调用作业责任结算。
  - 区别：被剔除的是**结果包**里的内容条目时，结果包照常提交；**任务**还没执行、输入已撤回时，任务本身跳过。
  - 理由：采集包承载的不只是内容，还有删除信号与"已可靠接收到哪里"的检查点。结果包以 `skipped_withdrawn` 结束会让纯删除包的墓碑丢失、检查点停滞（大纲 §4.7.2"快速通道不以目标正文可读为前提"）。

**不要做**

- 不信任 SDK 预跑结果。原因：worker 端代码可能被篡改或有缺陷；运行时侧重算并签名，才是可信依据（大纲 §4.7）。
- 计算段不等待网络。原因：会让任务的处理时间不可控，也可能在持有资源时被远端拖住。

**依赖与接口**

- 二组 SDK 是协议客户端（I1）与状态 API 客户端（I19）；证据库读取接口用于引用检查。

**测试与验收**

- 篡改结果包或伪造材料被拒；状态版本冲突返回 `state_version_changed` 并保留租约；PG 准入。
- 采集包剔除夹具：纯删除包；同切片 create 后 delete 折叠为空；内容条目全部已被撤回但带有效控制信号。三者都正常登记控制信号、推进检查点并结算作业。
- 根来源集合：遗漏任一类写入的根来源时，提交内适配器断言失败（与第 4 节联合）。

**必读大纲**：§4.2（引用检查）、§4.3（证据种类与写入方表）、§4.7（Worker 协议、ID 派生、计算段、digest、分段收口、提交结局）、§4.7.2（采集提交）、§4.12（写屏障与根来源）、§6.3。

## 4. 提交段（13 步）

**交付物**

- 13 步提交实现；全局加锁顺序与"不升级锁模式"。
- 普通回执与受限控制投影回执（独立操作类别）。
- 违规结局；第 ③、④、⑫ 步三处受限投影；第 ⑫ 步"仅检查点版本冲突"的补偿。
- **第 ⑥ 步锁集合**：按签名材料中的根来源集合，对文档与作者账号控制行按（范围类型，ID）排序一次性加锁；控制变更目标取所需最强模式。
- 在进程内调用二组事务内适配器（总册 §7.4.1）：第 ⑥ 步控制对象表与扇出（I7）、第 ⑧ 步证据库（I5）、第 ⑨ 步核验与观测（I9）与定时登记（I21）、第 ⑩ 步派生写入（I10）。I9 在 M0 末接入，接入前第 ⑨ 步不调用它。
- 锁序守卫与 failpoint 测试钩子。

**要研究的技术**

- PG 显式行锁与死锁检测；唯一约束的隐式等待；`INSERT … ON CONFLICT DO NOTHING` 幂等写入；`SET LOCAL`。
- 并发交错测试方法：双连接 + 命名屏障；Hypothesis 状态机测试。
- **multixact**：大量并发提交对同一热门账号控制行取 KEY SHARE 时会产生 multixact，要了解其年龄与成员空间的监控方法和 vacuum 行为。

**推荐实现与理由**

- **一个提交事务就是一个按步骤调用的函数**，配一个**锁序守卫**：记录"当前已到达的锁层级"，试图取更靠前层级的锁时直接抛错。CI 中常开，生产配置可关闭。
  - 理由：锁序错误在普通测试里很难暴露，往往要到高并发时才以死锁或数据错误出现。守卫能把它变成每次运行都能发现的确定性错误。
- **加锁一律用显式 SQL**，按（范围类型，ID）排序后批量加锁；同一对象一开始就取最强所需模式。
  - 理由：PG 不支持安全的锁升级，先弱后强会形成死锁（大纲 §4.7 明确"不得升级"）。
- **控制行锁模式**：普通引用 KEY SHARE；永久撤回 `FOR UPDATE`；临时原因 `FOR NO KEY UPDATE`；同一对象两类都涉及取 `FOR UPDATE`。**来源范围控制行不入锁序**，来源门控只在读时生效。
  - 理由：临时原因不参与写入资格比对，不应阻塞持 KEY SHARE 的普通提交；永久撤回必须阻塞 KEY SHARE，才能保证"删除后无有效写入"（大纲 §4.7、§4.12）。
- **事务内适配器以"传入提交上下文"的方式在进程内调用**：同一个连接、同一个事务；适配器声明所属锁层级，受同一个锁序守卫约束；适配器写入前断言根来源 ⊆ 已锁集合。
  - 理由：跨组调用是锁序最容易出错的地方，必须同一套机制兜住；经 RPC 或另开连接会破坏原子性，还可能等待自己事务持有的锁。
- **第 ⑧ 步遇目标实例 condemned**：整包返回 `retry_after(blob_condemned)`，不计失败；重提时由写入方在上传准备阶段重传（第 3 节）。
- **第 ⑥ 步新登记保守保持时，只生成"待登记的回访计时器"意图**（立即到期，带 hold\_id），在第 ⑨ 步经 I21 落库；第 ⑥ 步既不写定时表，也不直接创建任务。并入已有保持时不另建回访，也不重置已有的退避或核验预算。
  - 理由：定时表属状态行层级，第 ⑥ 步写入会与第 ⑧ 步取 blob 行锁构成反向取锁；在提交事务里经任务创建 API 建任务又会取作业行锁。计时器由定时服务在独立事务中建任务（总册 §6.7）。
- **状态行层级内部的固定顺序**：一组状态行（Agent 状态、PageResult、覆盖声明）→ I9（核验与观测、待确认撤回记录）→ I21（定时）→ I10（派生写入，第 ⑩ 步）；同一张表内按业务键排序。锁序守卫按此顺序注册。
  - 理由：同一层级里多张表的先后不固定，两个提交按不同顺序写就可能互相等待。
- **failpoint**：在"第 ④ 步前""④ 后 ⑫ 前""作业行锁内复核后、提交前"等命名点插入钩子，测试中可以阻塞，用于 M0 的交错夹具。
  - 理由：M0 硬判据要求在这些精确位置制造竞争，靠 sleep 无法稳定复现。
- **捕获死锁错误 40P01 后整事务回滚**，按瞬态重试，不计失败（大纲 §4.7）。

**不要做**

- 不用 SERIALIZABLE 隔离代替锁序设计。原因见 0.6 节。
- 不在提交事务内等网络，也不等别人的 pending 上传。原因：持锁等待外部事件会把锁持有时间拉长到不可控，并可能与回收作业互相等待（大纲 §4.3）。
- 不让 ORM 决定加锁时机。原因见 0.6 节。
- 不让事务内适配器另开连接或提交。原因见上。

**依赖与接口**

- 依赖二组事务内适配器：总册接口 I5、I7、I9、I10、I21（均无 Fake，直接用最小真实实现联调）。

**测试与验收**（M0 硬判据中的提交类）

- 并发与重复 complete 同回执；旧前沿 complete 返回 `segment_frontier_mismatch`。
- 同时引用并撤回同一对象、两个混合包反向包含相同对象、普通提交与删除并发：无锁升级、无删除后有效写入。
- 控制信号幂等与重算上限；纯临时原因包不阻塞并发 KEY SHARE 提交；锁序断言覆盖全部跨组调用路径与状态行层级内部顺序。
- "保持冲突 + 原始响应转正"的混合包通过锁序守卫（回访计时器在第 ⑨ 步落库）。
- `retry_after(blob_condemned)` 夹具：首次创建种类遇 condemned 后重传、以同一结果包重提成功。

**必读大纲**：§4.7 全部（重点：全局加锁顺序、提交段 13 步、提交结局）、§4.3（第 ⑧ 步相关、`retry_after(blob_condemned)`）、§4.12（写屏障、来源范围不入锁序）。

## 5. 外发箱与转发器

**交付物**

- 外发箱表、桶与桶租约（带代次）、单转发器。
- causal 键：每键只发布最早未确认项，按 `subjectseq`。
- arrival 键：按逐项 ACK 或连续已 ACK 前缀确认。
- 毒行隔离到外发死信并暂停该键；生产者配置启动校验。

**要研究的技术**

- Outbox 模式；Kafka 幂等生产者与 librdkafka 投递回调；ACK 乱序时的确认语义。

**推荐实现与理由**

- **转发器循环**：
  1. `SKIP LOCKED` 认领桶；
  2. 取最早未确认项发送；
  3. 回调中按（桶代次，租约，队头身份）CAS 确认；
  4. 出错即停桶、重建生产者，从最早未确认项继续。
  - 理由：业务结果和"要发的消息"在同一个提交事务里落库（外发箱），转发器只负责搬运；Kafka 暂时不可用也不会丢消息或回滚业务。CAS 确认防止旧转发器在接管后误确认。
- **Kafka 确认后才标记已发布**。故障接管允许重复，下游按事件身份去重。
  - 理由："至少一次 + 去重"比追求"恰好一次投递"简单可靠（大纲 §4.7.1）。

**不要做**

- 不用 Kafka 事务或 CDC 工具替代转发器。原因见 0.6 节。
- 不做多转发器。原因：Demo 单转发器足够，多转发器的分桶与接管列在 Phase 2-A。

**测试与验收**

- 转发器崩溃接管后不丢消息；ACK 乱序时不把已成功的后项当失败；毒行隔离。

**必读大纲**：§4.7.1、§6.1。

## 6. 采集作业：状态机、决策表执行、周期结算

**交付物**

- 作业表与状态机（idle / running / cooling / paused）、`job_generation`、检查点 CAS。
- 决策表执行：先做合法性校验，再匹配动作行，然后执行作业转换并创建后续任务；决策表计时器经 I21 在提交事务内登记。
- 违规结局受限投影；周期结算（periodic 与 continuous 固定时间窗）；恢复预算。
- **表外作业处置清单**（决策表之外改变作业状态的规则，集中维护在这里，新增须走变更流程；决策表本身不变）：违规结局与预算耗尽转 paused（大纲 §4.11）；断流临时门控经 I16 设置 `source_gap` 并转 paused（大纲 §4.12 M1 临时规则）；**接任空档处置**（总册 §6.8 第 2 步：本包决策表匹配行照常记入 PageResult 并另记处置原因与 `source_gap` 代次，检查点按决策表推进，作业先跨窗结算再转 paused，不创建续采，第 ⑨ 步不登记本包决策表计时器，受限投影路径不执行任何接任效果）；**M1 人工恢复采集**（总册 §6.5：经项目负责人审批，由二组核验完成检测器经 I16 恢复作业，门控不解除，按显式恢复结算并记录审批编号）。
- 采集任务全部终态调用作业责任结算；采集包剔除规则见第 3 节。
- 计划解析校验：`execution_form`、`continuity`、`supports_resume`、`worker_checkpoint`；**接收时刻证明能力闸门**（M1；最迟在接入真实来源之前交付，即软判据 S2 销项时；规则随 Manifest 契约在 M0 内定稿）：非夹具来源的 `control_delivery_bound.kind` 为 guarantee 的一律拒绝，不做静默降级（一期只对 http-fixture 来源开放，分册二 §3）。检查对象是执行配置锁里 Manifest 声明与来源配置合并后的有效值，来源配置的任何新版本进入执行配置锁之前都过同一检查。
- 决策表全组合穷举测试（CI 门禁，总册 §8.4）。

**要研究的技术**

- 决策表驱动的状态机；**显式笛卡尔积穷举**（`itertools.product`）与排除项断言；基于 CAS 的时间窗结算。

**推荐实现与理由**

- **判定器复用第 1 节的纯函数**；作业转换在提交事务第 ⑫ 步持作业行锁执行。
  - 理由：判定和执行分离，判定可以离线穷举测试，执行只在一处落库。
- **全组合用显式笛卡尔积穷举**：每个维度的取值域写成显式列表，`itertools.product` 生成全部组合；结构上不可能出现的组合列为排除项，每条排除都要有断言说明理由。决策表、违规清单或判定器变更时跑全量；其余时候夜间全量、PR 分片抽样。
  - 理由：H11 要求"全组合"，只有穷举才能作为证据；排除项显式断言，才不会把漏掉的组合误当作"不可能"。
- **continuous 周期在"窗口边界后第一次当前代次作业级事务"内逐窗结算**，用 `current_cycle_id` 的 CAS 保证只结算一次。
  - 理由：不用额外的定时器去"关窗"，避免计时器与提交并发结算同一个窗口（大纲 §4.11）。
- **切片任务身份为 **`(job, job_generation, slice_seq)`，`cycle_id` 只用于记账。
  - 理由：切片跨窗口边界时不会因为周期变化而断链（风险 R35）。

**不要做**

- 不让连接器决定下一步动作。原因：各平台接口千差万别，各自决定会让系统行为无法预测，也无法穷举测试。
- 计时器不得直接使在途任务失效。原因：计时器与在途提交会竞争，应由提交时的 CAS 统一拦截。
- 日历翻窗不隐式解除 paused。原因：paused 往往代表需要人工处理的问题，自动解除会掩盖故障（大纲 §4.11）。
- 不用随机生成代替穷举。原因见上。

**依赖与接口**

- 二组连接器产出 FetchPage；二组定时服务经任务创建 API 新建任务；二组 http-fixture 连接器驱动异常夹具；二组 I21 登记计时器。

**测试与验收**

- **M0**：
  - 决策表与违规清单全组合（H11，验收证据含组合总数、排除项清单与全量运行记录）；
  - 采集任务全部终态不残留无责任 running，旧代次终态不影响新作业；
  - 夹具 429 → 冷却 → 恢复，检查点按前缀推进；
  - 计划解析四类用例。
- **M1**：周期结算子项 M1-6.1–M1-6.8（总册附录 C）；能力闸门拒绝一例（总册附录 C 的 M1-8.5b）。

**必读大纲**：§4.7.2（采集提交）、§4.7 第 ⑫ 步、§4.11（作业段、FetchPage 字段、决策表、违规清单、判定规则、完备性测试、有界任务、fetch\_mode）、§8.4。

## 7. 作业代次变更协议

**交付物**

- 操作记录（operation\_id，以（job\_id，旧代次）唯一）、栅栏、默认终结目标；同一作业串行。
- 锁定全部非终态旧代次任务并绑定终结目标；改代次并使旧恢复计时器失效；旧代次心跳不再续租并返回停止指示。
- 扫尾器：只终结未领取或租约已失效的旧任务。
- 受限投影三入口（提交段 ③ ④ ⑫）与投影回执幂等；任一阶段崩溃后按 operation\_id 恢复。

**要研究的技术**

- fencing token 模式；多步操作的崩溃恢复（每步幂等 + 持久化操作状态）。

**推荐实现与理由**

- **操作本身是一个持久化状态机**：已登记栅栏 → 已绑定 → 已改代次 → 扫尾中 → 完成。每步幂等，恢复时从持久化状态继续，不覆盖已登记的目标。
  - 理由：代次变更跨越多个事务，中途任何一步都可能崩溃；只有持久化的操作状态加幂等步骤，才能保证恢复后不重复终结、不漏终结。
- **扫尾器由 operation\_id 驱动**。发现未在绑定阶段登记的旧任务时照样终结，并告警、按 operation\_id 审计定位绕过路径。
  - 理由：正常并发下不会出现这类任务（新建事务在作业行锁内复核），出现即说明有新建路径绕过了栅栏，必须暴露出来。

**不要做**

- 不用"中止操作"处理残留。原因：中止会让作业卡在变更中途，新旧代次都无法继续。
- 不终结租约仍有效的在途任务。原因：worker 可能正在读取包含删除事件的数据，提前终结会让墓碑丢失；等它提交或租约失效即可，最多推迟一个租约周期。

**依赖与接口**

- 二组定时服务只经任务创建 API 新建任务；二组 SDK 处理心跳停止指示。

**测试与验收**（M0 硬判据 H15）  
代次变更与提交竞争的全部夹具，按总册附录 C 子项 H15.1–H15.13 逐项登记：第 ④ 步前与 ④ 后 ⑫ 前两个屏障、扫描后出生的旧任务、锁内复核屏障、扫尾与在途 worker 交错（含租约到期后才到达的 complete）、代次变更终结后的迟到 complete（双连接、两个旧包、普通已完成任务拒绝不同摘要、回执丢失、崩溃）、operation\_id 四处崩溃恢复、连续两次变更、仅检查点版本冲突、cooling 期间计时器、多任务加锁顺序、扫描集合后才领取的合法竞争、cooling 期间发起代次变更。

**必读大纲**：§4.11（代次变更协议段）、§4.7 第 ③ ④ ⑫ 步与提交结局、§6.6、§13 M0 硬判据。

## 8. 控制状态转换、平台控制变更入口与本组删除处理器

**交付物**

- **统一的控制状态转换函数**：提交段第 ⑥ 步、采集"快速通道"和平台控制变更入口共用同一个函数。
- 永久撤回（文档 / 账号，写屏障）：递增撤回代次、分配撤回日志序号（单行计数器，`FOR UPDATE`）、登记扇出责任，按目标状态幂等。
- 临时原因（`account_inactive`、`sync_unverified(epoch)`、`source_gap(epoch)`）：
  - 只递增 availability 版本，不递增撤回代次、不分配序号、不登记扇出；
  - 比较基准三模式（可信上游事件时间 / 单一权威位置域 + handoff\_epoch / 按提交顺序）；
  - 状态未变也推进位置。
- 保守保持（保守 / 交接核对两类）、回访结果写回、覆盖前沿、覆盖证明、接收时刻证明（只用于实时送达；一期只对夹具来源启用）。
  - 回访：新登记保持时输出计时器意图，第 ⑨ 步经 I21 落库，由二组定时服务经任务创建 API 建回访任务；并入已有保持不另建回访、不重置预算（总册 §6.7）。
  - 接收时刻证明：只在来源送达上界合格且平台允许（一期只有夹具来源，分册二 §3）时使用。未启用时，原本需要这种证明、又不能经其他有效途径（如时间模式下的可信事件时间证明）证明的清除——例如回访确认"已设置"之后到达的账号恢复——一律登记或并入保守保持、经回访生效，**不得把"未启用"当成"无需证明"而按比较键直接清除**；正常有序清除与其他保持规则不变。启用时按上游事件身份经 I7 查询首次接收时刻与追赶标记，**不读结果包中的时间字段**：首次接收时刻减送达上界须严格晚于参照时刻才通过；首次接收带追赶标记或查不到记录的，该证明不通过，改走其他有效证明或保守保持。
- **平台控制变更入口（I16）**：供二组删除确认处理器、核验完成检测器、断流门控规则调用。在调用方开启的独立事务中执行，顺序为控制对象行 →（来源控制行 → 交接账号快照）→ 撤回日志计数行 → 所需状态行（按状态行层级的层内固定顺序）→ 作业 / 检查点行（如需，放在最后）；I16 返回后调用方不再追加写入。写入分两类：随控制结果产生的写入（扇出登记、新建保持的回访计时器、覆盖记录、交接快照的"已承接"标记）由转换函数输出决定，只在本次实际改变状态时执行；调用方的明确操作只限与控制结果无关的清理（如删除待确认撤回记录），回访计时器不属于明确操作，不因调用方传入登记请求而登记；请求本身无效时（如按代次清除而代次不匹配）整次不写入并返回拒绝。支持：
  - 缺失计数确认 → 永久撤回（即大纲 §4.12 的"独立删除事务"）；
  - `sync_unverified` / `source_gap` 的设置与按代次匹配清除；
  - 设置 `source_gap` 时把作业置 paused；M2 起按预授权条件清除时恢复作业并生成 partial 覆盖。
  - **M1 起：恢复作业、门控不解除**（总册 §6.5 的人工恢复采集）：请求必须带项目负责人审批编号，否则整次拒绝；只恢复作业（按显式恢复结算，授权依据记审批编号，覆盖记 partial），不改 `source_gap` 代次、核验切点与任何控制状态。
  - 控制状态按目标状态幂等；**目标状态已经达成时**（例如文档在处理器调用之前已由墓碑永久撤回），控制状态不变、不分配序号、不重复登记扇出，但调用方交来的清理类明确操作（如删除待确认记录）**仍照常执行**。接口 M0 末冻结，M1 前半可用。
  - 交接核对的分批承接与结束（总册 §6.8 第 5 步）；写入永久撤回时把待确认记录的确认依据（常规缺失确认 / 保守来源不可见撤回）记入撤回日志与审计。
  - **修改作业状态时与其他作业级事务一样**：
    - 在作业行上校验预期的 `job_generation` 与代次变更栅栏，不匹配则只登记控制状态、不改作业（旧代次的判断不得反向影响新代次作业）；
    - 计为"当前代次作业级事务"，跨窗口时先逐窗结算周期；
    - 恢复作业按大纲 §4.11 的显式恢复处理：先结算旧周期，再建新周期、重置预算、绑定新的恢复代次，并记录预授权条件编号作为授权依据。
- **位置域交接路径（M1，总册 §6.8）**：
  - **只有权威作业的显式切换报告或接任报告才建立 handoff**：连接器显式报告"本作业的实时连接从位置域 X 切换到 Y"，第 ⑥ 步在来源控制行锁内核对本包作业是第 ⑥ 步执行时的权威作业（经 I7 即时授权查询：在来源控制行锁之后执行，以该条查询语句为判定点，不传入请求开始等历史时刻，总册 §6.8 第 2 步）、且当前权威域等于 X，才登记 handoff\_epoch（两端位置、handoff 建立时刻）、把权威域改为 Y、经 I7 以一条集合式插入保存账号快照（账号集合见总册 §6.8 第 2 步；快照与"已承接"标记的锁层级在来源控制行之后、撤回日志计数行之前，第 ⑥ 步与 I16 相同，总册 §7.4.1）；需要交接核对时只登记"交接核对进行中"，不逐账号建保持。权威域已是 Y 时幂等；既不是 X 也不是 Y 时按非权威域处理。没有显式切换报告或接任报告、位置域又不等于权威域的包不建立 handoff，其中的账号临时原因事件只做记录、设置类登记保守保持，墓碑与永久撤回照常处理；旧域在 handoff\_epoch 之后迟到的账号临时原因事件同样无操作；非权威作业的显式切换报告同样不建立 handoff，本包按非权威域处理并告警。权威作业改指定到另一作业后，新作业带接任报告（两种报告都由连接器按检查点判断、重复携带，直到带报告的包以正常结局提交——正常结局时无论位点是否推进，检查点都记下位置域、指定版本与连续接收起点（被上游接受的续接游标，不是首条返回事件的位点，总册 §6.8 第 1 步）；本组对重复报告幂等；同一个包同时带两种报告时先按接任处理，显式切换报告只作审计）：来源控制行记下的权威域建立依据已是本作业、本指定版本时只做记录；权威域为空（来源首次启用）时只设权威域、不建立交接；权威域不等于其所在位置域时，以当前权威域为旧域、旧域最后已处理位置记为"未知"，按无法证明无遗漏登记 handoff 与交接核对；已等于时比较接任报告中的连续接收起点与**建立依据作业**（来源控制行记下的、最近一次建立或确认权威域的作业）检查点中该域的最后已处理位置（不加锁读取）：起点不晚于后者只做记录；晚于后者或取不到时（空档左端记为"未知"），**本组在同一次提交内执行接任空档处置**——第 ⑥ 步设置 `source_gap(新代次)` 并登记一条接任空档记录，第 ⑨ 步经 I9 登记该核验代次、切点记为"未确立"（连续接收起点不作切点，切点由二组恢复流程在可靠增量重新衔接时确立），第 ⑫ 步按第 6 节的表外处置把作业置 paused、不创建续采、不登记本包决策表计时器；转入受限投影的包不执行任何接任效果；不另开 I16 事务，二组不负责设置这个门控，只负责其后的核验与解除（总册 §6.8 第 2 步）。切换包内旧域部分先处理、新域部分在登记 handoff 之后处理；
  - **承接本次交接的核对责任（幂等操作，与后台分批承接共用）**：承接只适用于按位置域比较新旧的 `account_inactive`；`sync_unverified` 与 `source_gap` 按代次设置和解除，不建交接核对保持。处理该来源账号的 `account_inactive` 信号（含回访写回）之前，若该账号在快照中、尚未永久撤回、且该原因还没有记下本次 handoff\_epoch——已有未关闭保持时复用原 hold\_id 并记下本次 epoch（保守保持不降级、不另建回访、不重置预算，回访有效性还须晚于 handoff 建立时刻）；没有保持时新建交接核对保持（以 handoff 建立时刻作为登记时刻，计时器由转换函数输出、第 ⑨ 步落库）；已有本次完成记录时不重开；已永久撤回时只记录被覆盖，不建保持；经 I7 在该账号控制行锁内把快照中该账号记为"已承接"。然后按大纲规则处理（清除类并入不生效，设置类照常应用并并入）；
  - **来源控制行锁模式在计算段确定**：含显式切换报告或接任报告，或设置 / 清除 `source_gap` 时取 `FOR NO KEY UPDATE`；处理单一权威位置域来源的账号临时原因信号时取 `FOR SHARE`；都不涉及不加锁。两者互斥，不先读后锁、不升级；
  - 交接核对进行中又收到权威作业的显式切换报告或跨域接任报告时，登记新的 handoff\_epoch 与新快照，未关闭的保持记下新 epoch，不重复建保持；
  - 理由：几千个账号在一个提交事务里一次登记会让事务失控；交给后台慢慢建又会在空档里放过清除。按"首次信号前承接 + 后台分批承接"实现，效果等同于登记 handoff 时已为全部账号建好保持；只认权威作业的显式切换或接任，避免两个作业来回切换权威域；复用唯一保持，满足"每（账号，原因）至多一个未关闭保持"。
- **待确认撤回窗口的验收口径**：待确认撤回记录表示删除确认责任已经确定、不可撤销并立即禁读，但永久写屏障以 I16 提交为生效点；窗口内提交的写入照常登记完整根来源，永久撤回后由扇出处理器（含本组处理器）清理。M1 出口第 3 条"删除后写入被拒"以永久撤回生效为准。
- **撤回日志与发布（I8 发布端）**：日志在 PG 是权威；提交后经 LISTEN/NOTIFY 或外发箱事件**只做唤醒**；运行时 API `withdrawals_since(seq)` 供接收端按序号拉取、补齐空洞。
- **本组存储的删除处理器**（M1，注册到二组扇出登记表，纳入 CI"扇出登记对应"检查）：
  - Claim：标 `flags.source_withdrawn`，quote 遮蔽并留遮蔽记录；
  - ValidationRecord：标 `affected_by_deletion`；
  - EvaluationRecord：适用性失效；
  - 报告制品与 ReportInputSnapshot：受影响正文与下载制品禁读或遮蔽，按证据当前状态重新渲染；
  - ReviewRecord：复核文本、引语及其他内容派生字段遮蔽或清理，只保留允许保留的审计元数据；
  - Agent 状态存储中保存的内容派生数据：清除或遮蔽。
- 写入资格判定；所有写通道的屏障校验调用点。

**要研究的技术**

- 事件排序与比较器传递性（为什么不能"同域用位点、跨域用时间"逐对切换）。
- 时钟偏差与新鲜性区间推理；fencing epoch。
- 缺失观测计数规则（大纲 §4.11）：为了理解 I9 返回的"是否达到确认"以及何时调用 I16。

**推荐实现与理由**

- **规则写成"纯函数 + 薄事务外壳"**：
  - 纯函数输入：当前控制行状态、信号、来源比较基准配置、时间证据；
  - 纯函数输出：新状态、是否分配序号、要登记的扇出、要登记 / 并入 / 关闭的保持、要登记的回访计时器、回执注记；
  - 外壳负责按锁序加锁和落库；第 ⑥ 步与 I16 是两个外壳，共用一个纯函数。
  - 理由：这部分规则是全系统最密集的（大纲 §4.7 第 ⑥ 步）。写成纯函数后，可以用 Hypothesis 对乱序、重复、并发到达做排列测试，例如大纲 §8.3 的"三事件六种排列"；事务外壳很薄，锁序问题集中在一处检查。
- **锁模式**：临时原因取 `FOR NO KEY UPDATE`，永久撤回取 `FOR UPDATE`，同一对象两类都涉及时取 `FOR UPDATE`，不升级。
  - 理由：`FOR NO KEY UPDATE` 不阻塞只持 KEY SHARE 的普通提交，账号停用 / 恢复反复切换时不会拖慢正常写入；永久撤回必须阻塞 KEY SHARE，才能保证"删除后无有效写入"。
- **平台派生的变更走 I16，不另写转换逻辑**。
  - 理由：大纲规定删除信号只有一条正式路径（连接器 `tombstones[]`），缺失计数确认是平台派生的确认；两者都必须经同一个转换函数，才不会出现两套状态更新协议。

**不要做**

- 临时原因不阻塞持 KEY SHARE 的提交。原因见上。
- 不把平台观测时间写进上游比较键。原因：平台时间和上游事件时间不在同一时钟上，混用会破坏比较的传递性，产生比较环（大纲 §4.7 第 ⑥ 步）。
- 保守保持不判违规（V19）、不暂停作业。原因：无法定序是事务内依据当前状态才得出的结论，无法判断两个作业中哪一方有错；跨作业的提交顺序也不等于事件顺序，暂停反而会让旧事件覆盖新事件。
- 永久撤回对象不再生成保持与回访。原因：永久撤回不可逆，再回访没有意义，只会产生无用的人工待办。
- 不只靠广播传递撤回。原因：消息可能丢失，接收端必须能按序号从 PG 补齐。

**依赖与接口**

- 依赖二组：控制对象表 DDL、幂等创建与扇出登记、首次接收时刻与追赶标记查询（只在启用接收时刻证明的来源上使用）、交接账号快照与"已承接"标记、权威作业指定的即时授权查询（I7）；逐文档核验与观测（I9）；定时登记（I21）；扇出登记表（本组处理器注册到这里）。
- 提供给二组：I16、I8 发布端与 `withdrawals_since(seq)`。
- 回访任务由二组的 collector 执行，结果经本组提交路径写回。

**测试与验收**

- M0：控制信号类硬判据 H13（子项 H13.1–H13.6）、H7a、H9。
- M1：大纲 §8.3 Bluesky 行夹具中归本组的子项（总册附录 C 的 M1-8.2、8.3、8.4、8.5b、8.6a、8.8b）；I16 与交接子项 M1-D9.1–D9.5；I16 幂等与崩溃重跑；本组删除处理器（含"复核文本含原文"的夹具）纳入删除全链路夹具。
- M1：人工恢复采集只恢复作业、门控不解除，无审批编号被拒（M1-D9.6）。
- M2：预授权自动恢复按显式恢复结算（M2-D6.1）。

**必读大纲**：§4.7 第 ⑥ 步全文、§4.11（缺失观测计数、逐文档核验）、§4.12、§3.3（撤回控制通道）、§8.3（Bluesky 行）、§9（控制对象行、保持记录、覆盖证明字段）。

## 9. 合并触发、回放隔离、有状态切换（M2）

**交付物**

- 合并触发：每键一个在途任务 + 刷新标记 + `max_staleness`，结果绑定输入快照；话题合并带 epoch。
- 回放隔离：独立命名空间、初始快照、allowlist、预算、虚拟时钟；不恢复已删内容，不重新采集。
- 影子 → 晋升；背压与入口限速：**阀门策略由本组定义**，执行点在采集入口，由二组在 M2 实现。
- 有状态切换六步：停派发 → 排空 → 封旧代次 → 迁移核对 → 原子切换 → 积压派发。Demo 只允许第 ⑤ 步前回退。

**要研究的技术**

- 虚拟时钟注入；按命名空间路由的存储隔离；状态迁移与 `state_compare` 核对。

**推荐实现与理由**

- **执行上下文携带模式与命名空间，存储门面按命名空间路由**；回放从 PG 事件表生成任务。
  - 理由：隔离在门面层统一执行，Agent 代码不用区分自己在 live 还是 replay 模式，也就不会因为某个 Agent 忘记判断而污染正式数据。
- **阀门放在采集入口**。
  - 理由：在源头限流，比在中间环节丢弃更可控，丢弃留痕也集中（大纲 §6.3）。

**不要做**

- 回放不重新采集、不恢复已删内容。原因：重新采集会产生新的外部读取，恢复已删内容违反删除义务（大纲 §6.5）。
- 不支持第 ⑤ 步之后回退。原因：原子切换后回退需要反向迁移状态，Demo 只允许前滚，"切换后回退"列在 Phase 2-B。

**测试与验收**

- **M0**：live / replay 隔离。
- **M2**：插件完整流程；有状态升级覆盖排队、在途、迁移失败、旧提交、回退边界。

**必读大纲**：§4.6（模式权限表）、§6.3–6.6。

## 10. Agent 开发框架、样例与桩

**交付物**

- 一个最小样例 Agent，作为模板：Manifest + `handle(tasks)` + Claim 构造 + 证据绑定 + flags 传递 + acceptance\_policy 引用。M0 末交付。
- Agent 开发指南、本地运行与测试工具。
- **Agent 桩**（M1）：富化（enricher-\*）、分发（distributor）、auditor、cost-monitor。返回 `simulated / skipped`，**永不返回 **`delivered`，模拟标志沿链传播。

**要研究的技术**

- Manifest 全字段（大纲 §4.4）；SDK 接口；Claim 质量语义与五态；ID 派生规则。

**推荐实现与理由**

- **样例选"关键词标签器"一类简单逻辑**，走通"领取 → 读证据 → 产出 Claim → 提交 → 外发"整条链路；新 Agent 一律从模板生成。
  - 理由：M1 要并行开发十多个 Agent，统一模板能保证 Manifest、证据绑定、标志传递这些容易漏的地方从一开始就是对的。
- **桩按桩化规范（Null / Fake / Real 同工厂）实现**。
  - 理由：后续替换为真实实现时只改工厂配置，下游不改（大纲 §2.3）。

**不要做**

- Agent 不直接访问数据库、网络或文件系统（文件系统只读，例外只有 tmpfs 和声明的缓存目录）。原因：直接访问会绕过状态管理、撤回屏障、网络策略和缓存失效机制（底线 2、3、4）。
- 不把 LangChain、LlamaIndex 等框架当作运行时。原因见 0.6 节。

**必读大纲**：§2.2（八条底线）、§2.3（桩化规范）、§2.4（代码分层）、§4.2、§4.4、§4.7（ID 派生）、§5（Agent 目录与档位）。

## 13. 报告

**交付物**

- 报告契约实现：内容块 + 六种槽位（`fact:metric_result_id`、`derived`、`time`、`entity`、`quote`、`cite`）。
- 就绪判定两级结论（完整 / 相对本次观察），读取 CaptureCoverage、处理前沿与核验状态（I9 查询）；ReportInputSnapshot（短事务冻结，读取经 I17 读时可用性判定）。
- 槽位校验：等值替换须匹配主体、时间窗、单位、结果身份。
- 发布策略合并（取最严）、人工审批流、制品 ID / 版本 / 审批 digest。
- 删除后按证据当前状态重新渲染或遮蔽（处理器见第 8 节）；报告请求 API。
- **按演示模式渲染**（总册 §12）：报告快照只存假名化后的内容；查看与导出时按当前演示模式渲染——内部模式经二组的假名反查服务显示真实作者标识，外部模式调用二组的遮蔽库做全部假名化；导出制品带模式标记，导出登记（I20）记下导出时的模式。
- 下载等导出：先经导出登记（I20）登记副本与受控 / 非受控分类，登记成功后才把制品交给用户；制品生成与生成失败的处理由本组负责。

**要研究的技术**

- 模板引擎（Mustache，或 Jinja2 沙箱环境）；结构化生成（模型输出带槽位引用的中间表示）。
- CaptureCoverage 与就绪判定逻辑。

**推荐实现与理由**

- **report-drafter 先生成"内容块 + 槽位引用"的 JSON 中间表示，再由模板渲染**。
  - 事实统计数字用 `fact:metric_result_id` 槽位引用指标结果；
  - 日期用 `time` 槽位，派生数值用 `derived` 槽位，各自按其校验规则核对；
  - quote 槽位必须能定位到原文；
  - **槽位之外的正文不得出现模型自己写的数字**（槽位外文本扫描）。
  - 理由：模型只负责组织语言和选择槽位，数字与引语由平台填入并校验，每个数字都可追溯、每句引语都可核对；把日期与派生数值也硬塞进指标结果会误拒合法内容。中间表示也便于在删除后按证据当前状态重新渲染。
- **渲染时按证据当前状态过滤**，已撤回证据显示原因与审计元数据。
  - 理由：已发布报告受删除影响时，不能继续展示已删原文（大纲 §4.8）。
- **先登记、后交付**。
  - 理由：没有登记就交出去的副本，删除时无从追踪。

**不要做**

- 不让模型在槽位之外写数字。原因见上。
- 不在非沙箱模板环境中渲染不可信内容。原因见 0.4 节"模板"一行。

**依赖与接口**

- 二组：指标目录与知识服务（I12）、核验状态查询（I9）、读时可用性判定（I17）、导出登记（I20）、证据读取接口。

**测试与验收**

- **M1**：两级就绪结论驱动报告（unknown 来源只能"相对本次观察"）。
- **M3**：未撤回部分可复验，撤回部分展示原因与审计元数据。

**必读大纲**：§3.2（就绪判定、ReportInputSnapshot）、§4.8、§4.12（报告与导出）、§7（指标目录）。

## 14. 校验规则、评测与复核

**交付物**

- **ValidationRecord 契约与存储表由本组定义**（第 1 节）。
- **M0：校验库执行骨架与规则插件接口（I14）**，按总册 §7.3 决策点 1 自二组转交（0.3，设计见分册二 §15，二组保留接口评审），直接复用 ValidationRecord。
- 校验库规则：M1，基于本组 M0 骨架。
- ValidationRecord 六维（同步 / 异步 / 不适用）、版本化 `acceptance_policy`、Claim 五态状态机，以及状态对可达性 CI。
- evaluator：逐条评测，EvaluationRecord 不可变；n = 0 显示"评价未知"，n \< 30 带区间。
- **区分"规则基线评测"与"组合评测"**：评测记录标明所用的模型资源；全规则基线或模拟输出的评测只能作阶段开发与基线评测，不能当作大纲"范围界定"要求的"模型 + 提示词 + 检索 + 规则"组合评估（总册 §7.3 决策点 2）。组合评估的验收归属见总册 §7.3：实现中含大模型环节的谓词，只有含大模型的组合运行记录才算组合评估；M1 出口时资源未到位的，M1 出口第 10 条按基线记录登记为允许遗留、注明资源缺口，M2 出口前以组合运行补齐（总册附录 C 的 M1-10.1）。"资源未到位"按项目负责人登记的到位日期判定（缺省：晚于 M1 出口前两周到位即按未到位处理）；含大模型环节的谓词以 M1 第 1 周登记的清单为准，清单变更（例如把某个谓词改成纯规则实现）按总册 §11.1 二级处理（本组组长 + 项目负责人审批），变更说明写明对组合评估覆盖范围的影响；M2 的组合运行补跑计入本组 M2 剩余必做工作，按总册 §7.3 与 §10.2 处理。
- **评测语料的构成**（项目负责人已拍板，一期只用免费且无需申请的来源，分册二 §16）：中文文本主要是市场监管官方公告与政府网站发布、美团 ASAP 餐饮点评与 Bluesky 上的中文帖，缺少中文网民投诉原文。评测记录注明语料构成；某个谓词真实样本不足时如实标注 n 与区间（n = 0 显示"评价未知"），不用合成语料补数（大纲 §11）。
- **组合评估的模型资源**（项目负责人已拍板）：用 DeepSeek API；评测记录注明模型与版本；M2 出口前切换为平台内 Qwen 的，切换后的组合重跑组合评估，DeepSeek 上的记录不沿用。
- review-queue：复核队列与 ReviewRecord，复核文本不贴原文；ReviewRecord 登记删除处理器（第 8 节）。
- golden set 管理（与标注人员配合）。
- 聚类集合级与排行评测：M2 调节阀 0.3，与二组的漏报 / 端到端评测是两个独立验收条目。

**要研究的技术**

- 小样本比例区间（推荐 Wilson 区间）；标注一致性度量；漏报评测方法（与二组 M2 的漏报 / 端到端评测衔接）。

**推荐实现与理由**

- **小样本区间推荐 Wilson 区间**。
  - 理由：样本量小或比例接近 0 / 1 时，常用的正态近似区间会给出不合理的结果（例如超出 0–1）；Wilson 区间在这些情况下表现稳定，计算也简单。
- **评测与复核用的真实样本同样受删除约束**：样本来源被删除时，EvaluationRecord 适用性失效（第 8 节处理器）。

**不要做**

- 不设统一"可信等级"分数。原因：单一分数会掩盖"用了什么方法、校验结果如何、依赖了什么"，大纲 §4.2 要求展示方法徽标 + 验证结果 + 依赖标志。
- 来源删除只设 `flags.source_withdrawn`，不改 Claim 状态。原因：状态表示结论本身的生命周期，删除是读时生效的外部事实，两者混在一起会让状态机不可达性检查失效（大纲 §4.2）。

**测试与验收**

- **M1**：每个必做谓词有带 n 与区间的逐条评测记录，记录注明所用模型资源（M1-10.1）；复核队列可用；Claim 五态可达性门禁通过。

**必读大纲**：§4.2（质量语义、五态）、§4.6（模式与可见范围）、§4.10（知识快照）、§4.12（评测、复核与标注的删除约束）、§7（评测体系、准确度杠杆）。
